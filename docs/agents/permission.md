## 规则：三条决定

- **三条决定，按这个次序判出来，而次序就是那条不变量**：按命令的**分段** —— 一条 `deny` 规则命中 →`Deny`；内置的结构化 `rm` 守卫触发 → `Deny`；一条 `allow` 规则命中 → 那个分段对 ask 规则是**豁免**的（它不是白名单：什么都没命中也照样跑）**且整条命令回来的是 `DecisionAllowExempt`**，命中的模式跟着决定一起回来，就像 deny 的那样；一条 `ask` 规则命中 → 记住它并继续扫（后面的 segment 仍可能拒绝）。整条命令：任一 `Deny` → 拒绝；否则任一 `Ask` → 询问；否则有 allow 规则命中时 `DecisionAllowExempt`，否则就是普通的 **allow**。所以 `allow` 的意思是「这里不需要例外」，绝不是「只有这一条能跑」。
- **`DecisionAllow` 和 `DecisionAllowExempt` 是两个值，因为调用方会按这个差别行动**：一个裸的 `Allow` 是「没有任何东西覆盖到它，所以它按默认就跑」——这正是判断门禁存在的那个群体——而 exempt 那个形式是用户自己对恰好这个形状给出的答案，也正是它把那次调用上的门禁关掉。一个 segment 的 allow 规则绝不会盖过另一个 segment 的 deny，而一条没有被任何 allow 规则覆盖的 segment 上的 ask 规则仍然成立。
- **segments 来自一个真正的解析器**（`mvdan.cc/sh`、`permission.Segments`）：管道、`&&`/`||`/`;`、命令替换和重定向各自成为自己的 segment，引号被尊重（`echo "a;b"` 是一个），heredoc 的**正文**是数据、永远不会成为 segment，而开头的 `sudo ` 会按 segment 剥掉，所以 `sudo rm -rf /` 能命中为 `rm` 写的规则。一条规则只会看到规范打印形式——这就是为什么同一份输出喂给判断门禁的状态（见下），以及为什么在任何地方再放第二个解析器都是一个 bug。
- **一条无法解析的命令是带哨兵值 `permission.AskNoRule` 的 `ask`**，而不是一次规则命中——无论调用方对这个群体做什么，它都不能声称命中了某条规则。要记在心里的形状是**未闭合的 heredoc**：bash 会跑它（在输入结束处把 body 收尾），而我们的解析器对它实际作用的东西一无所知。末尾的 `&&` 或未闭合的引号——最常见的两个——bash 也会拒绝，所以在那里的 `ask` 只是噪声。
- **内置保护**是两套不同的机制，而 `disable_builtin_deny`（只在**全局**配置里——项目文件不能削弱它）把两者都关掉：`permission.BuiltinDenyRules`（磁盘覆写、关机/重启的 glob，由调用方前插到用户的 deny列表）和 Policy 内部的**结构化 `rm` 守卫**，它针对根目录、它的直接子项和 `$HOME`——故意不是一个 glob，因为 `rm -rf /*` 也会把 `rm -rf /tmp/x` 一起吞掉（更深的绝对路径属于用户策略，设计使然）。

## 询问（ask）这条路：三种原因、四个答案

- **三种原因、三种措辞，任何东西都不得把它们混为一谈**（`askCause`、`askReasonLine`）：一条命令要么命中了一条 `ask` 规则，要么无法解析（`AskNoRule`），要么是因为什么都没命中而被判断门禁弹出来的。用第一种的句子去渲染第二或第三种，会让读者去自己的配置里找一个他们从没写过的规则。当判断同意时，真规则赢得措辞，因为用户自己的话才是他们认得出来的。**文件工具的 ask 只有第一种和第三种，永远没有第二种**——路径总是能解析——所以 `AskNoRule` 只属于命令那一半，绝不能写进一个路径原因里。
- **四个答案，由每个 agent 的 `PermissionMode` 选择**：`TUI` 弹问（`y` 本次放行 / `a` 本会话放行 /`n` 拒绝，后者会**中止**这一轮——文件工具的拒绝只拒绝那次调用，这一轮继续，见它那一节）；`External` 委托给一个 `PermissionHandler`（桌面端的卡片、ACP 的 `session/request_permission`）；`Skip` 会**批准**这个 ask，它是每一个没有人可问的入口模式——channel、`tachi -p`、子代理、dream、那些一次性命令。一条命中的 `ask` 规则是用户在要求运行前先咨询他；没有人可咨询时，拒绝会让一次没人能解开的运行卡住，所以那些入口会跑它，而 `deny`（在 ask 分支之前就判定）才是那里仍然说不的东西。`Skip` 也从不判断（见门禁那一节），并且在不问任何人就批准的情况下，不写任何 `[permission]` 记录。
- **ask 的预览是 agent 写的，不是前端写的**（`askPreview`：先是主题，然后是为什么——主题对 Bash ask 来说是那条命令，对文件 ask 来说是调用方写下的工具加路径）。桌面端原样显示它——那个格式的第二个渲染器会有自由漂移的空间，而原因那行才是人去行动的那部分。
- **拒绝的文本被塑造成让模型停下来，而不是向它解释配置**：事实（未执行）、规则、谁能改它（用户），以及一句明确的「不要换另一种形式尝试同一件事，不要去读那些权限文件」。**任何拒绝都不得点出一个配置路径**，也没有一条被写成邀请你去查点什么——点出那个文件正是让一个乐于助人的模型跑去读它的东西（`TestBashRefusalsDoNotInviteInvestigation`）。现在拒绝只可能来自 `deny`：一个 `ask` 里已经没有拒绝留着了（接上的前端把它交给一个人，无人值守的模式批准它）。
- **`deny` 在任何 ask 被弹出之前就判定了**，所以 ask 这条路上没有任何东西能碰到它：不是会话级批准，不是权限处理器，也不是判断门禁。那个性质是调用图的，不是要记住的约定——加一步的时候也要保持这样。

## 判断门禁（Jev）

- **`permissions.bash.jev: auto`（默认）| `off`**，叠在一个可用的 `jev:` 块之上。`auto` 的形状和 `mcp_tool_search.matcher` / `cron.notify_matcher` 一样：只要服务配置好了，门禁就跑。
- **它判断每一条未被拒绝的命令，而它只能做两件事**：跑它，或者弹出本该由规则弹出的那个 ask。它从不产生 `deny`——概率不是保证，而一个 99% 时候都正确的 `deny` 就是坏的（jev.md）。一条被判到量表顶端的灾难性命令也只是被升级给一个人看，这正是要点。有两个东西会把它关掉：**用户写的一条 `allow` 规则**（见下），以及按**会话**的「本会话全部允许」（见下面的会话级批准）——一个没人能对它行动的裁决不值得花那次调用。
- **一条 `allow` 规则是让一整类命令不再被判断的决定性做法**——而它是唯一一个按形状而不是按会话起作用的杠杆，这很要紧，因为门禁给出的答案正是用户不断遇到的东西（在真实流量上测过：几乎每一个 ask 都是 `ssh <host> '<script>'` 这一类工作，而没有任何阈值能把它和该问的命令分开）。`CheckBash` 把命中的模式报为 `DecisionAllowExempt`，于是 `checkBashPermission` 在门禁之前就返回了——什么都不判，所以也不写 `[permission]` 记录，完全就像那条命令上不存在这个门禁一样。它坐在 deny 分支之后，所以一条 allow 规则绝不会扩张成去跑一条 deny 禁止的东西。改成把这条规则当作另一个**状态事实**传给判断曾被测量过，收益约0.02（见 `docs/2026-09-30-bash-ask-jev-design.md`）——规则必须做决定，而不是给建议。
- **只在人能回答的地方**：`PermissionModeSkip` 被排除，所以一个 channel bot、一个子代理或 `-p` 绝不会有一个概率替它们批准什么。放任它这样做会是一个产品决策，而不是这个门禁的事。
- **当服务回答不了时，由规则决定**：规则命中的命令问，没命中的跑。这就是为什么一次故障不能让任何东西变得更糟，以及为什么一次失败绝不会被这条会话 latch 住（下一条命令再试一次）。
- **它也不能放宽一条 ask 规则**：门禁开着时，一条命中 ask 规则的命令确实会被判断，而「run」的裁决会把它放过去——这就是「自动批准」的意思，也是用户必须知道的那一个行为（`config.BashPermissions.Jev` 自己的注释就是这么说的）。如果你哪天想让 ask 规则保留否决权（「命中 ⇒ 问，绝不判断」），那是 `checkBashPermission` 里的一个分支——但那样门禁只覆盖没命中那一半。上面那条 allow 规则是相反的情形，而且是有意为之：用户写来**豁免**一个形状的规则做决定，而一条只说「先问一下」的规则会被判断。
- **一个会话记忆（每个 agent 一份）存的是概率，阈值在读取时才应用**（`PermissionState.askVerdicts`）：改 `jev_threshold` 会重新判定已经判过的命令，而键是（规范命令，命中规则）——不会对一条自身没被判定过的命令推断任何东西，`ClearSession` 会丢掉这张表。
- **客户端是懒建的但会被留着**（`agent_permission_jev.go`）：每条命令重建一次会丢掉连接池并为每次握手付费，而那正是这个门禁成本的大头。缓存以它被构建时所用的块为键，所以一次设置保存会重建它，而不需要任何推送管线。
- **一次判断不是一次 provider 调用**，所以计费装饰器从来看不到它：门禁写自己的账本行（`llm.RecordJevUsage`、`UsageKindJev`，含信用快照）。跳过它会让这些调用在 `/usage` 里看起来是免费的。

## 文件工具：路径规则 + 它们的门禁

- **三个文件工具（`ReadFile` / `WriteFile` / `EditFile`）有各自的规则集，共享一道门禁。**`permissions.files.read|write|edit` 是路径 glob（`deny`/`ask`/`allow`，与命令规则同样的优先级）；`permissions.files.jev` 是盖在三个之上的一个 `auto|off` 开关，只有一个 τ——工具名是状态里的一个**事实**，而一个阈值属于那个问题，所以在一个测出来的数上放三个开关，就会在一个数的地方出现三个数。
- **一条路径规则的 `allow` 和命令侧那个意思一样——读法也一样**：`CheckPath` 返回带命中模式的 `DecisionAllowExempt`，`checkFilePermission` 在判断之前返回，什么都不问、什么都不记。它是一个仅限**全局**的列表（`allow` 从不来自项目文件），所以它能做的是让用户把一个在自己那些树之外的目录——例如 agent 一直往里写导出的一个暂存目录——彻底豁免于判断。
- **一条规则有两种形式，两者都是承重的**（`permission.PathPattern`）：`Text` 是用户写下时的原文——`~/.ssh/*` 保持 `~/.ssh/*`，一个项目的 `secrets/*` 保持 `secrets/*`——它是 ask 预览、拒绝和判断的状态回引的东西；`Canonical` 是字面前缀已解析后的锚定形式，匹配器比较的就是它。只按 text 匹配，在一台通过符号链接到达某个目录的机器上会静默地永不触发（macOS 的 `/etc` → `/private/etc`）；只按规范形式命名，会引用一条用户在自家配置里找不到的规则——又是 issue #40 的故障，这也是为什么 `Text` 也不是展开后的形式。两侧都走 `permission.CanonicalizePath`，这就是为什么它只有一个函数。
- **`canonicalPattern` 用字符串拼出结果，绝不用 `filepath.Join`**——而这是一个**陷阱**，不是风格选择：`Join` 会做 clean，所以 `Join("/a", "")+"*"` 出来是 `/a*`，一条不再覆盖那个目录、却覆盖每一个名字开头相同的**兄弟路径**的规则（`/a-backup`、`/a2`）。一个只测匹配器的用例看不出来（`*` 跨 `/`，所以放宽后的模式仍然匹配那条规则本来针对的文件）——方向按列表不同：一条 deny 过度拦截，一条 `allow` 过度豁免。`TestCanonicalPatternKeepsTheSeparator` 同时断言那个字符串和 sibling 的行为。
- **锚定，以及分层规则**：`~`（以及任何相对的全局模式）在全局配置里锚定到 home，而 `<tree>/.tachi/permissions.yaml` 里的相对模式锚定到那一棵树；`allow` 仅限 global，所以一个项目只能收紧。路径这一半和命令那一半在同一个 `Policy` 上（`WithFileRules`）：一次重建、一次会话切换、一次重置。
- **读也会被判断。** 判据不是「它写不写东西」——`~/.ssh/id_rsa` 和一个项目的 `.env` 是最清楚的需要看一眼的情形，而它们是读。同样被判断的还有状态能作为事实陈述的那一个边界：目标是否落在会话工作的那些树之内。
- **状态描述的是目标，绝不是 payload。** 路径（规范的）、stat 对它说的东西、会话的工作目录和那些树，以及命中的规则——绝不是一次写会放进文件的内容，也不是一次编辑的两半。payload 是模型生成的自由文本，那正是 `jev.md` 警告的语域陷阱，而且它会让状态随所写的东西一起长大。这个代价是被测量过、并且被点名写在 `config.FilesPermissions.JevThreshold` 自己的注释里的：内容在状态里时，一次对 `.tachi/permissions.yaml` 的写得了 0.87，不在时是 0.43——所以**是规则、而不是判断，在阻止一个 agent重写它自己被判断所依据的那些规则**。
- **一次拒绝拒绝的是这次调用，绝不是这一轮**（`resolveFileAsk`），不像 bash ask 的 `errCancelled`；一个 `deny` 仍然在到达门禁之前就判定了。在 `PermissionModeSkip` 下门禁完全关闭，而一条命中的 ask 规则由那个模式的分支批准——和命令那一半同样的读法，也是为什么没有任何无人值守的文件调用会为一条 `ask` 被拒绝——没有任何出厂配置带文件规则，所以默认行为没有变化。
- **`Read` 和 `Edit` 是可并行的工具**（`Write` 不是）：门禁在两个执行器上都跑，而一次被挂起的 ask 会在 `PermissionState.askMu` 上串行——一条 `ConfirmResp` 通道服务整个 agent。那行 `[permission]` 通过 `notes[i]` 切片走出一个并行组，一个 goroutine 一个下标。
- **它的 τ 属于 `pkg/jev/testdata/files-ask.json`**，不属于任何别的东西——不属于 `permissions.bash.jev_threshold`，那回答的是另一个问题。出厂的 τ = 0.60——走廊 (0.49, 0.62) 的顶端，所以它对每一次例行调用的读法都一样，但正坐在最近的需要看一眼的用例下面 0.02 处——是在那个用例集上扫出来的（64 次调用 × 5，`jev-1.13.0`）；它刻意漏掉什么、以及什么时候该重扫，写在 `config.FilesPermissions.JevThreshold` 自己的注释里，而扫描历史在 `docs/2026-09-30-files-ask-jev-design.md`（允许过时）。它与 `jevask` 在**形状**上共享的那几个渲染器（未知值占位符、上限那行）是故意重复的：一个共享函数会让一句改过的话同时废掉两个阈值——那行目录树**已经不再共享**了，`jevask` 后来把它去掉，`jevfiles` 这边还留着。用 `agent/permission/jevfiles/generate_cases_test.go` 重新生成用例文件。



- **没有任何阈值是一个事实。** `confidence` 的意思是「分布有多集中在**这个**调用方给出的那些选项上」，所以问题、判据、**状态形状**和模型版本都属于任何一个 τ。它被记录在 `config.BashPermissions.JevThreshold` 的注释里，**连同用例集和模型版本**，而重扫是移动它的唯一方式。当端点服务的是一个**别名**而不是一个版本时，在同一个注释里说明这一点：那个数字于是是一个关于没人钉住的权重的假设（jev.md，「A pinned model」）。
- **状态的事实集属于那个判断，不属于这一层碰巧持有什么。** 出厂的 τ = 0.66——所测窗口 (0.62, 0.70) 的中间——是在一个只有这些事实的状态上扫出来的：规范的 segments、工作目录、以及命中的规则（或者为什么没有命中）。它曾经还带第四个事实，**会话工作的那些树**，为了一条（「碰到工作树之外的数据」）后来被删掉的判据：那条轴被测过，而它正是这个门禁在真实工作上有噪声的全部原因（见 agent/permission/jevask 的包文档）。**改动状态渲染的任何一句话，这个数字就作废。**
- **一条判据才是杠杆；判据不读的一个事实是死重。** 同一个测量就是这么说的：只把状态里那行 trees 删掉，例行命令的判定几乎不动；而把「在树之外」那一句从判据里删掉，它们的判定会大幅移动——那些本身危险的命令则纹丝不动。不要试图靠从一个门禁那里拿走上下文来让它安静——把那一句删掉，否则它会继续按它判断。
- **那次删除之后，bash 门禁问的是什么**：命令**到底**做了什么——读凭据、改动或发布共享状态、重写历史、运行从网络取来的代码、删除无法重现的工作，或者走遍一整个文件系统或一棵无界的树（最后一个是判为 Yes 的那一侧唯一的只读形状：一个**时长**原因，故意保留、也刻意的不与作用域挂钩）。
- **只要事实，绝不要一个推导出来的裁决。** 「在树之外：否」会被当成一个事实消费，而这里一个错的事实是不对称的（它能把一条命令说到阈值之下）。一个空事实写「(unknown …)」，而不是编一个出来。
- **一个标签必须能从门禁看到的东西判定**——命令被写下来时的样子，绝不是如果 shell 拒绝了它会怎样。（一个反着归档的用例会把走廊清空。）
- **不要把用户的单轮消息放进状态。** 判断回答的是那条**命令**是什么；一个请求是上下文而不是许可，而自由文本正是 jev.md 警告的语域变量。它还会破坏会话记忆的键。（`bash-ask-context.json` 就是敲定这件事的配对测量——差值在噪声内。）
- **一次重扫是什么**：从 `agent/permission/jevask` 重新生成用例文件（它的生成器；状态文本必须来自生产装配器，绝不手写），然后 `JEV_EVAL_FILE=bash-ask.json go test ./pkg/jev/ -run TestJevEval -v`。语料是 `pkg/jev/testdata/bash-ask*/`；`bash-ask-context.json` 就是上面那个配对实验，留着是为了让这个结论保持可复现。
- **高 τ 会漏掉 ask；低 τ 只会打断。** 坐在走廊安全的那一侧，而当有什么看着不对时，重读逐用例表而不是摘要。

## 会话级批准

- **「本会话全部允许」是一个答案配**两个**读者——只翻转其中一个，就是这个形状存在的意义所在的那个 bug。**策略的那一份（`Policy.AllowAllAsksForSession`）让一条命中的 ask 规则不再问；agent 的那一份（`PermState.AllowAllAsks`）让两道判断门禁不再问，两者都在自己的 deny 分支之后、判断之前读它——所以门禁根本不被咨询（一个没人能对它行动的裁决不值得一次调用，而它会弹出的那张卡片正是用户刚刚关掉的那张）。两个读者不是冗余：策略的那一份是一个 fork 出来的子代理与它父级共享的东西（`agent_fork.go`），而 PermState 那一份是在一个会话根本没有策略时（规则不存在**且**内置保护被关掉——它的门禁照样会问，而它的按钮曾经什么都不做）唯一存在的那一份。一个 setter 翻转两者：`AIAgent.AllowAllAsksForSession`。
- **deny 在到达任何一个读者之前就判定了**，所以「别再问我了」绝不会变成「去跑我禁止的东西」。它确实会放宽进去的那一个 ask 是无法解析的命令（`AskNoRule`）：什么都没被解析，所以没有任何规则——包括 deny——看到过它的任何一部分，于是那条命令就凭这个一揽子答案跑起来。这是故意的，也符合每一个无人值守前端（PermissionModeSkip 自己就会批准两种策略 ask 中的任一种，因为没有人可咨询），而这个群体是良性的：一个未闭合的引号，或者末尾的 `&&`。
- **重建一份策略必须**继承**策略那一半**（`InheritSessionApprovals`），否则一次文件夹变更会重新问一个用户已经答过的问题——一个他们无法预见的退化。PermState 那一半不需要继承（一次树变更重建的是策略，不是 agent）。**规则**绝不能带过去：它们正是变掉的东西。
- **结束一个会话会丢掉两半**（`ResetSessionApprovals` + `PermState.AllowAllAsks`，来自 `ClearSession`）——连同门禁的记忆，因为一个新对话不是那个命令被判断过或放行过的对话。
- **桌面把这个答案做成了一个可见的模式**：输入框下方那行状态栏里那个下拉框（「需要审批」／「无需审批」）读写的是**会话记录**自己的字段（`session.Session.SkipApproval`），写成功之后才翻 agent 上那两个读者（`AIAgent.SetAllowAllAsksForSession`，那个唯一的 setter）。所以卡片上的「本会话全部允许」仍然是**这一进程里**的一个答案，而「无需审批」是持久的：换个会话、重启应用都跟着它。两条相反的规矩都是故意的：压缩出来的新会话**不带过去**（`FinalizeCompact` 的白名单里没有这个字段——那是一次新的对话，没人被问过它要不要审批），而**分支**带着它（跟 thinking level / skip_dream 一样，是读者对这个对话的长期选择）。切回「需要审批」会把 agent 上那个开关一起清掉，包括同一进程里某张卡片答过的「本会话全部允许」——下拉框是这个答案的可见形态，它说「要问」就不能实际不问。它只回答 bash 与文件工具那个问题：MCP 搜索费用卡片的会话答案住在自己的字段上（见下一条），不跟着动。冒烟：`perm-approval-off`。
- MCP 搜索成本卡片的会话答案（`MCPSearchAllowed/Blocked`）出于同样的理由住在这旁边，但它们回答的是另一个问题（钱，不是规则）——而它自己的开关才是让那张卡片的「本会话全部允许」一开始就能工作的东西，这个形状就是从这里抄来的：不一致的是权限卡片，不是搜索卡片。

## 哪些目录树贡献规则

- **规则是按树的，会话工作的**每一棵**树都贡献**：`AIAgent.SetPermissionTrees(ctx, primary, additional)` →`config.ProjectRootsFrom`（每个目录向上走到它最近的 `.git`，按顺序去重）→ 每一份 `<tree>/.tachi/permissions.yaml` 被读入并取并集。`allow` 保持仅限 global，所以一个项目只能收紧。只读主树那份文件是一个朝**更坏**方向的洞：用户在第二个仓库里写的一条规则会静默地不触发。
- **`PermissionRoot` 命名主树；`PermissionTrees` 是那一整组**——后者才是判断门禁的状态所报告的东西，因为没有全部那些树，「在树之外」毫无意义。
- **前端自己拥有那个解析器，而且它必须和它们提示词用的是同一个**：桌面端的 `sessionRootsFrom`（四个调用点：agent 构造、`beginTurn` 的那一个 stale 标志，以及设置里的两行——`permissions.bash` 和 `permissions.files`）、ACP 的 `roots.Cwd()/Dirs()`（四个：三个会话构造器，以及那个改 `additionalDirectories` 的内存中 resume）。一个自己解析树的新调用点，就是 desktop.md 的「桌面会话树」那一节描述的 bug。
- **`configure` 从进程 cwd 构建**，而对一个 GUI 应用来说那就是 `/`——所以更清楚情况的前端会在第一轮之前重新指向它（桌面端和 ACP 都这么做）。

## 结果上那行 `[permission]`

- **两道门禁写同一行，而它只去事件——会话全文——绝不进模型的消息**（`agent.askNote`，`checkBashPermission` 和 `checkFilePermission` 都会写）：`[permission] decided_by=judgment score=0.180 threshold=0.660`，或者对一次被问过并获批准的调用 `decided_by=approval`（无人值守的分支不问任何人就批准，所以它不写记录）。一次**失败**的调用也会追加它（那次调用跑了，或者被拒绝了，两种都一样），而没有判断也没有 ask 就完全没有这一行，所以一次平平无奇的调用的结果和门禁存在之前是逐字节相同的。
- **模型是刻意拿不到它的。** 模型那一侧有两个代价：一行模型不会据此行动的东西，会在之后每一次请求的历史里被重新发送（event 不在历史里），而「这一条被放行了」摆在模型面前，会诱使它把它读成对同类命令的一种长期许可。所以 Bash 工具的描述也不带关于它的任何一句——一句描述会在每一次请求上搭上一个模型永远看不到的数字，而文件工具的描述也都一句不带。人的另一个出口是 debug 日志（`Agent: bash ask judged` /`Agent: file ask judged`，每次判断一行，带概率、阈值和裁决）。
- **成对出现，绝不是一个光秃秃的数字**：在 `judgment` 下那个分数是让它跑起来的概率，在 `approval` 下它是让门禁去问的那个概率。
