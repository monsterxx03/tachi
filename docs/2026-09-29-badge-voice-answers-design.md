# 设备上的语音输入：把「三键打不了字」这件事绕过去

> 状态: 方案。**主机侧的可行性已经实测**（多轮探针，数据见附录 B）——§4 的格式、§7 的接法、
> §10 的语言判据都是**量出来的**，不是推的；**P0-②（Swift 垫片链路）已经跑通**（代码在
> `desktop/stt/`）。设备侧尚未开工。还剩三件待定，见文末。
> 关联: [2026-09-28-agent-badge-link-design.md](2026-09-28-agent-badge-link-design.md)（链路与协议的基础）、
>       `desktop/link/link.go`、`desktop/agent_turn.go`（`SendMessage` / `Steer`）、

> 设备侧仓库: `FoloToy/ai-passport`（`main/badge_voice.c` 等，见 §6）

## 1. 要做什么

**让设备能说话**——说出来的话变成**当前活跃会话的一条消息**。

基础那份设计里有一条明确不做：「不做设备端自由文本输入。三键打不了字，模型提的『无选项填空题』
在设备上显示『需要在电脑上回答』」。这条限制的真实代价是：**人不在电脑前时，除在选项里点一下
之外什么也说不出来**，而这块设备存在的全部意义正是「人不在电脑前」。

**绕过去的办法是分工，不是妥协**：设备只当话筒（采集 + 压缩 + 发上去），**转写在主机**。
设备依然打不了字——限制没被违反，它只是不再是终点。

**v1 只有一条用途**：在**主屏**（没有在等的问题时）长按确定说话，转写出来的文本送给 desktop 的
**当前活跃会话**——和你在输入框里敲一句话、按回车是**同一件事**：

- **那个会话没在跑** → 开一个新 turn（`SendMessage`）。
- **那个会话正在跑** → 排进队列，等 agent 的 **steer 点**注入（`steer_check` → `Steer`）。
  这包括「agent 正卡在一条 ask 上等你回答」那种情况：文本会一直排在队列里，直到你把那条问题
  答掉、agent 走到下一个 steer 点。**这是明确接受的代价**（§8 有一条）。

**明确不做**（原先那两条用途都取消）：

- **不用它回答 ask**：不绑 `ref`、不走 `AnswerQuestion`——在设备上回答问题的入口仍然只是那几个键。
- **不用它给权限拒绝补理由**：协议里那个一直没人用的 `annotations` 字段继续空着。
- 也不做设备端转写（算力与功耗不该花在这上面）、不做常开麦克风（§8）、不把音频当聊天的多模态
  输入喂模型（要的是**文本**，不是第二套语义）、**不走 llm provider**——本机就能转，还不用联网（§7）。

## 2. 为什么是「设备只当话筒」

与整条链路同一条架构原则：**语义留在主机**。设备不知道 `allow_once` 是什么意思、不知道自己在不在
前台、不知道用户在看哪个会话——同理，它也不该知道「这句话是什么意思」。它只负责把一段声音变成
一串字节送上去。

**「发给哪个会话」也归主机**：活跃会话是 desktop 前端的当前选择，设备手里没有这个信息（它只知道
「谁在等我回答」）——所以 §5 的消息里**没有会话 id**，这是有意的，不是漏了。

顺带三个好处：转写模型/服务换了设备端一行不用改；设备端要测的仍然是纯逻辑（采样没到下限、
超了上限、链路断了怎么办）；音频**不进**设备的历史，不占它的 flash。

## 3. 交互

**主屏长按确定说话**。

- **为什么是主屏**：**有等待问题的那些屏一个字都不改**——那里长按确定仍然是提交（核心操作，
  抢它会毁掉现有手感）。
- **主屏上要挪走一个既有手势**：长按确定原来是 **「忘记配对的电脑」**（两按确认），它挪到
  **长按上**（`BADGE_KEY_PREV`，主屏上原本空着；`main.c` 的 `handle_key` 按 `ask_count == 0`
  判「在主屏」）。其余键位不动。

```
    ┌──────────────────────────┐
    │      （主屏，没有等待）    │   ← 标题栏照旧
    │ ┌──────────────────────┐ │
    │ │ 长按确定说话          │ │
    │ └──────────────────────┘ │
    │ ● 录音中 3.2s / 6s       │   ← 录音时：红点 + 已录时长 + 上限倒计时
    │ 松手发送 · 确定取消       │   ← 提示跟着手势走（和翻屏那套一致）
    └──────────────────────────┘
```

- **开始/结束**：按下即开始采集；**松手即结束并发送**。
  - BSP 的按键事件是 `PRESS / CLICK / DOUBLE / LONG`——**没有 release**。所以「松手」靠轮询
    `bsp_button_read_mv()` 判：录音任务每 50ms 读一次那个 ADC 节点，回到松开档位就是松手。
    （函数本来就有，是留给分压标定的；只读，不碰按钮组件自己的采样。）
  - 备选：改成 toggle——长按开始、再长按结束，上限自动停。手感差一截，但完全不依赖 ADC 时序。
  - **实际实现用的是 toggle**（`badge_voice_toggle`）：第一次上真机时先把「采集 → 编码 →
    上传」这条路跑通，不去赌 ADC 时序；「按住说话」留到 P2，那时才有手感可谈。
- **上限**：到**上限**（6 秒，见 §4 的时长账）自动结束并发送——不让人录到链路塞满才发现。
  实现里**没有**做「短于 0.3s ＝误触」那条：toggle 模式下长按本身就要几百毫秒，再判一次
  时长只是多一条几乎没人会走到的路径（真改成按住说话时再加，见 P2）。
- **发送中**：换成「发送中… 3.1s / 5.0s」（按已发送字节数，取自 `voice_end` 之前的进账）。
- **结果**：**录完直接发**，屏幕上给一行 —— 「已发送」+ **转写文本**（设备不回改文本：不满意
  就重录）。会话在跑时是「排队中（会话在跑）」，因为那时它进的是队列、要等一个 steer 点
  （§5 的 `state`）；这句提示不是装饰，它是唯一能让人分辨「送到了」和「还在路上」的东西。
  - **两条都实现了**：录完先显示「已发送 4.3s 的语音」（用时长让人知道自己那段上去了
    没有），转写完了再补一行 `已发送：<转写出来的字>`；会话在跑时那一行是「排队中：…」。
- **取消**：录音中短按确定＝丢弃（手滑了不用发上去）。这需要屏幕说清楚，否则「按一下没了」
  很像坏了。

## 4. 传输与格式：先把带宽量出来

这段是这件事的**工程核心**，而且**第一件事是量**——不是估。

**Step 0（动手第一件事）**：让设备吐 64 KB 假数据、主机侧计时。**已经量完（P0-①）**：

| 项 | 实测 |
| --- | --- |
| 可持续吞吐（**原始**字节） | **12.6 – 13.3 KB/s**（设备侧 13271 B/s / 主机侧 12.6 KB/s，两侧独立算出来的数对得上） |
| 64 KiB 用时 | 4.9 – 5.1 秒，**128/128 片，一片不丢** |
| 这条链路的余量 | 对 **8 KB/s（16 kHz ADPCM）约 1.6 倍**；6 秒的语音 ≈ 3.8 秒传完 |
| 结论 | **16 kHz 站得住**，不必退到 8 kHz（§10 那个「按带宽二选一」现在有答案了） |

**怎么打通的（这是这次量出来最有用的东西）：BLE 的发送必须有背压。**
notify 提交受**两个**缓冲约束，而且它们是不同的东西：

- 本地 mbuf 池 —— `ble_hs_mbuf_from_flat` 返回 NULL；
- 控制器/HCI 的 ACL 缓冲 —— `ble_gatts_notify_custom` 返回 `BLE_HS_ENOMEM`。

两者都在链路层把前面的包发出去之后才腾出来，所以「发不出去就**等 10 ms 再试同一块**」是
必需的，不是优化：没有它时，一条 720 字节的行连发到第 4 片就再也提交不出去（64 KB 里只有
3 KB 到得了主机），而设备屏幕上看到的是「已发 4 片，失败 124 片」。等的是 10 ms 而不是
1 ms —— 回收周期是**一个连接事件**（这条链路上约 40 ms），不是 CPU 调度。

另外两件配套的事：

- **NimBLE 的 MSYS 块要调大（`MSYS_1_BLOCK_SIZE=640`）**：内部上限 `BLE_ATT_ATTR_MAX_LEN`
  是 512，而默认 256 的块装不下一条 253 字节的 notify，于是每条都要**跨两块**，池的消耗
  翻倍（而且 `_os_msys_find_pool` 不会跨池兜底：它选中哪个池，那个池空了就失败）。
- 重试只覆盖**能重试的**错误：`BLE_HS_ENOMEM`（缓冲类）值得等，别的（没连接、没订阅）
  重试也没用。失败的那一块没发出去、前面的块已经发完，所以重试同一块**不会留下半行**
  ——半行才是要避免的（§5）。
设计文档里已经有一条反面教材：BLE 上一次写超 182 字节会被静默丢掉，而那个上限是**实测**出来的。
同样的道理，这条链路的**可持续吞吐**必须实测，否则所有的「几秒能传完」都是猜。

**格式**：**单声道 / IMA ADPCM（4 bit）**，采样率**由 P0 量出的可持续吞吐二选一**：

| 方案 | 码率 | 6 秒的字节数 | 什么时候用 |
| --- | --- | --- | --- |
| **16 kHz / IMA ADPCM** | 8 KB/s | 48 KB | **首选——实测吞吐 13 KB/s，1.6 倍余量** |
| **8 kHz / IMA ADPCM** | 4 KB/s | 24 KB | 带宽不够时的退路（现在没这个必要了） |
| 8 kHz / 16 bit | 16 KB/s | 96 KB | 不用：比 16 kHz ADPCM 更费带宽，识别还更差 |
| 16 kHz / 16 bit | 32 KB/s | 192 KB | 不用：链路撑不住 |

三条实测结论：

1. **8 kHz 大体不掉分，但不是零代价**。11.2 秒的长句上，四种变体的转写错误确实同一量级
   （复现过，附录 B 表 3，逐字一致）；但**短句上见过一次明显退化**——`最后 push 到 main`
   里的英文词整段变成汉字（`最后通时到内`，附录 B 表 7）。8 kHz 是拿识别率换带宽，不是白拿的，
   所以它降级成退路。
2. **ADPCM 4:1 不掉分**。手工实现的 IMA ADPCM 编码→解码往返之后，转写结果与无损输入同级
   （有的句子甚至更像对的）。所以「省带宽」这件事在识别率上**不要付代价**——尽管付。
3. **原生输入只有 8 kHz / 16 kHz 两档**（附录 B 表 1）。设备端按哪档采样都不用重采样，
   主机端也一样。

**采样率定成一个命名常量**（和 BSP 的 `BADGE_*` 一样放在一处），值由 P0 的带宽数字按上表选，
**时长上限 = 字节上限 ÷ 码率**同样由它推出来。

剩下的唯一约束是**链路可持续吞吐**，而它已经量出来了：**13 KB/s**（§4 的 Step 0）。
所以 30 秒的 16 kHz ADPCM（240 KB）在链路能力上约 18 秒传完——但**实际上是边录边传**，
录完时绝大部分已经上去了（实测：14.3 秒的录音，传输用了 14.37 秒，与采集同步，没有积压）。
**时长上限按 30 秒定**：它不是链路给的限制（链路 13 KB/s > 采集 8 KB/s，再长也撑得住），
而是「一句话」的合理长度。

**分片**：`base64` 编码（4/3 膨胀），每片 512 字节原始数据 → 一条 ~700 字节的 JSON 行。
设备侧的发送路径本来就按 MTU 切片（`badge_ble_send`），所以一条 700 字节的行 = 3 个 notify，没问题。

## 5. 协议（设备 → 主机，外加两条回执）

沿用行分隔 JSON + `@@` 前缀，三条新消息：

```json
{"t":"voice_begin","seq":51,"id":7,"codec":"ima-adpcm","hz":8000,"bytes":24576}
{"t":"voice_chunk","seq":52,"id":7,"data":"<512 字节的 base64>"}     // × N
{"t":"voice_end","id":7,"parts":96}
```

- **为什么不是一条大行**：一条 64 KB 的行要求双方一起把它捧在内存里，中途失败就整条重来；分片
  之后丢一片只损失一片，而且**进度可见**（设备能显示「已发 3.1/5.0 秒」，这在一条大行上是做不到的）。
- **`id` 是设备自己的自增号，不是 `ref`**。`ref` 在主机的语义是「哪一条 ask」，而语音**不属于任何
  一条 ask**（§1）——它只用来把回执对回这一次传输，所以由发起方（设备）给。
- **`bytes` / `parts`**：让主机能提前发现「收不满」（链路断了），而不是把半截音频送去转写。
- **主机 → 设备的两条新消息**（`state` 是「你那句话到哪了」的全部答案）：

```json
{"t":"voice_text","seq":54,"id":7,"text":"帮我把这个改动提交一下","state":"sent"}
{"t":"error","seq":55,"id":7,"message":"转写失败：本机语音识别不可用"}
```

  - `state` 只有两个值：`sent`（已经开了一个 turn）或 `queued`（会话在跑，文本进了队列、等一个
    steer 点）。设备据此显示「已发送」还是「排队中」（§3）——没有第三个状态，因为主机也没有更多
    的信息可给。
  - 失败一律走现成的 `error` 回音：没有活跃会话、本机识别不可用、音频太短、解码失败、超时。
    屏幕上有字，胜过「按了半天没反应」。
- **不需要新的主机→设备消息类型来撤屏**：那个 `ask_gone` 是给回答用的，这条路用不上（设备自己
  在收到 `voice_text` 之后撤掉那行提示）。

**这条链路上的信任边界没变**：BLE 那条已经要求「已认证加密」才说话（MITM 配对 + 6 位码）；
语音是**内容**，和屏幕上那些字同级。TCP/WiFi 将来照旧需要应用层密钥（基础那份文档 §9.1）。

## 6. 设备侧实现

**已经落地的那半**（真机验证过：4.35 秒的录音 = 68 片 34816 字节、一片不丢）：

- `main/badge_adpcm.{c,h}`：IMA ADPCM 编码器。**纯逻辑**，与 `tools/stt-probe/adpcm_roundtrip.py`
  逐字节一致（`tests/test_badge_adpcm.c` 钉着那份 Python 跑出来的向量）。
- `main/badge_voice.c`：三条消息的编码（纯逻辑，`tests/test_badge_voice.c`）。
- `main/badge_voice_task.c`：录音任务——唤醒 codec → 按 32 ms 帧采集 → 编码 → 攒成 512 字节
  一片 → 上传 → flush → 把 codec 睡回去。它在自己的任务里，因为 `bsp_audio_read` 会阻塞
  （BSP 的硬规矩：PCM 读写必须待在 worker task 里）。
- `main/main.c`：主屏长按确定 → `badge_voice_toggle()`；结果由 app 循环取回来显示
  （状态机只由 app 任务碰）。另外那个「峰值」自检也在这里读数：**录到了但没声音**要和
  「链路成功」分开说。
- 与提示音的 codec 互斥（§8 那条）：录音时提示音丢弃（`badge_voice_busy`），提示音在放时
  不允许开始录（`badge_sound_busy`）。

**回执也接了**：主机转写完会回一条 `voice_text`（§5），屏幕上显示「已发送：<那几个字>」
或「排队中：…」；录音中那 30 秒里，底栏是**倒计时**（`● 录音中 3.2s / 30s`），而录音中
短按确定＝丢弃这一段（`badge_voice_cancel`，主机按 end 里的 `parts=0` 把已经收到的那些片
整段作废）。

下面是最初的计划，逐条仍然成立（采集与编解码已经按它落地了）：

- **`main/badge_voice.c/.h`：自己的任务，独占麦克风**。理由和提示音一样：`bsp_audio_read` 会阻塞，
  而按 BSP 的硬规矩，PCM 读写必须待在 worker task 里、且休眠前要停掉 I/O。
  - 采集：`bsp_audio_set_format(<§4 定的采样率>, 16, 1)` → 按块 `bsp_audio_read` → IMA 编码 → 入队。
  - 发送：编码后的片交给 `send_line`（那条既有的出方向路由，BLE/串口不用它操心）。
  - 结束：停采集 → （音频不睡，因为提示音那条也用它；两处共用一把「谁在用 codec」的约定，
    见 §8 的边界）。
- **状态机多一态**：`BADGE_VOICE_IDLE / RECORDING / SENDING`，放进 `badge_state`（纯逻辑、主机可测）：
  「什么时候能开始录」（**只有在主屏、且没有在等的问题时**——§3 那条手势的边界也在这里，不散在
  UI 代码里）「录多久必须停」「松手后还能不能取消」都是纯判定，不需要硬件。
- **界面**：录音 / 发送 / 结果各一屏（或主屏上一个覆盖层，替换掉提示区），提示音那条规矩照旧——
  **录音中不熄屏**（屏幕上正显示时长与上限，熄了等于把手上的操作藏起来）。
- **协议编码**：`badge_proto.c` 加三条编码（纯逻辑、主机可测，和 `answer` 的编码同一套写法）。

## 7. 主机侧实现

- **`desktop/link`**：`Server.handle` 认这三条消息 → 按 `id` 攒进一个缓冲区（有上限、有超时的
  半截会话表：链路断在中间不会永久留着一块内存）→ `voice_end` 时交出 `[]byte`，并回一条
  `voice_text` 或 `error`（§5）。
- **解码**：IMA ADPCM → PCM（~30 行，放 `pkg/audio`？见待定 3）。
- **转写走 macOS 自己的 `Speech.framework`**，不走 llm provider（两者都不需要：本机就能做，而且
  **不联网**）。用的是 macOS 26 的新 API（`SpeechAnalyzer` + `SpeechTranscriber`），**不是**老的
  `SFSpeechRecognizer`——理由见下面第一条，这是实测查明的：
  - **⚠ 这套新 API 只有 Swift 有**。`SpeechAnalyzer` / `SpeechTranscriber` / `AssetInventory`
    在 ObjC 头文件里**不存在**，只有老的 `SFSpeechRecognizer`。所以**不能**照抄
    `desktop/webview_awake_darwin.go` 那个「内联 ObjC」的模式——那条路走不通。
    **垫片必须用 Swift**：`desktop/stt/shim.swift`，由 `build_shim.sh`（挂在 `go:generate` 和
    `make` 的 build/test 上）用 `swiftc` 编成 `libtachi_stt.a` 再链进来；`stt_other.go` 给非
    darwin 一份「这台机器没有这个能力」的桩。**这是这个方案引入的唯一一处新构建环节**，
    已经跑通（见本节末）。
  - **原地（on-device）识别，没有配额**。新 API 全是本机模型，音频不出机器；老 API 那个
    「每天 1000 次」的上传配额与我们无关。
  - **喂 PCM 走 `AnalyzerInput(buffer:)` 的流式入口，不写临时文件**：§8 承诺了「音频不落盘」，
    为了转写破掉自己的承诺不值得。**这条路已经实测通了**（附录 B 表 8）：裸 Int16 样本包成
    `AVAudioPCMBuffer`（`commonFormat: .pcmFormatInt16`）→ 喂 `AsyncStream<AnalyzerInput>` →
    `analyzer.start(inputSequence:)` → `finalizeAndFinishThroughEndOfInput()`，结果与
    `analyzeSequence(from: AVAudioFile)` **逐字一致**，每块 512 还是 1600 个样本也一样。
    所以垫片的入参就是「`[]int16` + 采样率」，全程不碰磁盘（`./run.sh 6` 可复现；分块大小
    随便挑，时序上让 `start` 与灌数据**并发**就对了）。
  - **语言与资产**：`SpeechTranscriber(locale:preset:.transcription)`。资产用
    `AssetInventory.status(forModules:)` 查；`installed` 才离线可用，否则要
    `assetInstallationRequest` + `downloadAndInstall()`（**这一步联网**，是一次性的）。
    本机实测：`zh_CN` / `zh_TW` **预装**；`en_US` 要下载一次，装上就常驻——本机现在是
    `en_IE, en_ZA, en_SG, en_US, en_AU, en_NZ, zh_TW, en_GB, en_IN, en_CA, zh_CN` 十一种
    （`SpeechTranscriber.installedLocales`）。所以**只认中文的机器零下载**；要判英文
    （§10），第一次会联网下载一次。
    没资产**不能装死**：回一条 `{"t":"error",…}`，屏幕上看得到。
  - **异步 + 超时**：识别是 `async` 的。Go 这侧用一个带超时（~30 秒）的等待把结果收回来；卡住
    不能把回答这条路径一起挂住。
  - **一个新的 TCC 权限**：`NSSpeechRecognitionUsageDescription`（`Info.plist` 与 `Info.dev.plist`
    都要加，和蓝牙那个键同一个位置——**已加**）。⚠ 和蓝牙那次一模一样的坑：授权归因给
    **responsible process**，而且判定发生在**第一次调用**时——所以老 app 包里的二进制会静默失败，
    测试从 app 里跑也会继承它。（探针正是因此在 `.app` 里跑，而不是裸 CLI：裸 CLI 的
    responsible process 是终端，终端没有这个键，结果是直接崩。）
- **投递**：转写出来的文本交给 desktop 的**当前活跃会话**，走和「用户在输入框里敲一句话」
  **同一条路**：空闲时 `SendMessage` 起一个 turn；在跑时进**前端的 pending 队列**，等 agent 的
  `steer_check` 到来时由前端调用 `Steer` 注入。**已实现**：`desktop/badge.go` 把文本
  `Emit("badge:voice")` 出去，前端 `composer.tsx` 收下后调它自己的 `submit()` —— 那是 diff
  面板那条「发给 agent」用的同一条路，所以「按确定说话」和「敲回车」在后端眼里是同一件事。
  - **为什么队列必须留在前端**：那份队列就是「会话在跑时用户敲进去的东西」这个概念本身
    （`composer.tsx` 的 pending queue），agent 停在 steer 点上等的是**它**。Go 侧另存一份，
    就会有两个队列争「谁先被注入」。所以 Go 侧只把文本交出去（一个事件），由前端决定立即发
    还是排队——它本来就负责画那个气泡、也负责让人能取消队列里的某一条。
  - **哪个会话是「当前」的也归前端**：事件里只有文本、**没有会话 id**（§2 那条），因为那
    是 desktop 前端的当前选择，设备手上没有这个信息。
  - 由此也自动继承了前端的既有行为：转写文本与敲进输入框的文本走同一套展开（`@file` 之类）、
    同一条乐观气泡、同一个「排队中」的显示。
- **垫片这一环已经跑通**（P0-②）。`desktop/stt/` 把整条链一次问通——Go → cgo → Swift →
  Speech.framework → 异步资产查询 → Swift → cgo → Go；测试断言的是**内容**而不是「没报错」：
  `available=1 installed=…（十一种）supported=30`。所以主机侧代码的前置不再存在，剩下的是
  §4 那个带宽数字（P0-①）和协议那一条链（P1）。三个坑——部署目标必须是 12.0、`swiftc` 的
  产物是一个**构建步骤**、以及链接要多一条搜索路径（back-deployment 兼容库在 toolchain 里、
  不在 SDK 里）——都记在 `docs/agents/desktop.md` 里。
- **不动的东西**：协议其余部分、状态机、设备 UI 的其余屏、提示音。

## 8. 边界与失败

- **麦克风只在按下与松手之间开着**。没有常开、没有「环境音」模式——这条要写进代码注释，也要
  写进 README：一块放在桌上的设备，麦克风的行为必须是可以一眼说清的。
- **音频不落盘**。整段留在内存里，转写完即丢（要不要留档见待定 3）。
- **链路断在录音中间**：`voice_begin` 已经发出去了，主机那边攒了半截——靠超时丢掉（§7）。
  设备这边显示「发送失败」，用户重录。**不做断点续传**：一条 6 秒的留言不值得。
- **没有活跃会话**（桌面上没开任何会话）→ `error` 回音，屏幕上写「没有活跃会话」。这不是异常，
  是正常状态：语音的归宿是一个**具体**的会话，没有会话就没有归宿。
- **排队可能等很久，而且这是接受的**：agent 卡在一条 ask 上时，「steer 点」要等那条 ask 被回答
  才到——所以设备显示的是**「排队中」而不是「已发送」**（§3、§5 的 `state`）。v1 不为此做打断：
  这是一句话，不是插队。（真要插队＝停掉当前 turn 再发，desktop 里有 `StopAndSend` 那条路，
  留作待定。）
- **与提示音共用 codec**：两边都碰 ES8311（提示音要放、录音要收），而 BSP 的约定是「调用方串行化
  格式/休眠/唤醒，且切换前停止所有 PCM 读写」。所以要有一把锁（或一个「codec 现在归谁」的约定），
  否则「正在录音时来了一声提示音」就是一次格式互踩。**这是这件事里最容易出错的地方。**
- **低电时**：录音 + 传输是最费电的一幕（麦克风 + 射频同时开）。要不要在电量低于 N% 时拒绝录音，
  见待定。
- **一秒能录多长**：上限自动停；短于 0.3s 丢弃；连按不叠加（有状态机兜着）。

## 10. 待定（还剩一件）

1. **音频要不要留档**：默认不留（内存里转写完即丢）。要留就落在 `~/.tachi/` 下某个目录，
   并且默认关——一块桌上的设备悄悄留下人声是另一类东西。

### 已经定了的

- **ADPCM 两份实现各自归位**：设备侧的编码在 `main/badge_adpcm.c`，主机侧的解码在
  `pkg/audio`（业务无关的纯逻辑，按仓库规矩进 `pkg/`）。两边都有各自的测试，而它们
  **逐字节对齐**——这一点用同一组向量在两侧钉住（设备侧对着 Python 探针，主机侧对着同一份）。
- **时长上限 30 秒**（`BADGE_VOICE_MAX_MS`）。它不是链路给的限制——链路 13 KB/s > 采集
  8 KB/s，实测 14.3 秒的录音一片不丢、与采集同步（§4）——而是「一句话」的合理长度。

### 已经定了的

- **识别用哪个语言**：**默认 `zh-CN`，并且要能认英文**（配置项 `voice.locale` 是兜底）。
  - **判据：先看有没有汉字，再比置信度**。一个 analyzer 同时挂 zh + en 两个 transcriber，两边
    **各自独立**转写整段音频（不是按语种分段拼接——`SpeechDetector` 只报「有语音/无语音」，
    不判语种）。但我们要的不是**融合**，是**选**，而 `transcriptionConfidence` 正好够用：
    **zh-CN 的结果里出现汉字就用它**（覆盖绝大多数），**一个汉字都没有时**才跟 en-US 比置信度。
    六句话 × 三种音频（16 kHz 无损 / 16 kHz ADPCM / 8 kHz ADPCM）**18 次全对**，见附录 B 表 6
    （复跑第 5 轮 17/18：**第二层判据在纯英文句上是脆的**，反例与边界见表 6 末尾）。
  - **为什么不单比置信度**：**第一层（汉字）是主要依据，不是保险**——第二层真的会出错。复跑里
    就有一次 zh-CN 0.56 对 en-US 0.55（差 0.01）、而 zh 那串是音译垃圾（附录 B 表 6 末）；
    当初那批也有一次「残缺却自信」的半句（en-US 给 `Hi, R S S I, her battery level. Hi`、
    conf 0.67，zh-CN 0.80，只差 0.13）。置信度说的是「我说得对不对」，不是「我听全了没有」——
    所以字符构成那条硬规则比它可靠。
  - **代价是耗时约 2×**：同一段 11.2 秒音频，单模块 ~150 ms，双模块 ~280 ms。相对于传输可以忽略。
  - **中英混说：zh-CN 一个模块就够用**。中文句子里嵌的英文词大多能出来（`commit` / `revert` /
    `RSSI` 都活着），会糊的是不常见的那些：`desktop`→`Destok`、`link`→`Lin`、`ble`→`fla`、
    `read`→`Rid`、`main`→`man`、`go test`→`gotest`。en-US 模块识别中文是垃圾。
  - **`DictationTranscriber` 不用**。它是另一套模型（`preset: .shortDictation`），
    `transcriptionConfidence` **恒为 0**（根本不报这个属性，判据直接失效），质量也明显更差：
    `commit revert` → `to meet river`、`lint` → `领`、`BLE` → `RSI`。淘汰。
  - **两条纠错路都堵死**：`AnalysisContext.contextualStrings`（偏置词表）**完全无效**——把目标词
    原样放进词表，输出一字不差；`preset: .transcriptionWithAlternatives` 的备选**只是尾部碎片**
    （`隔。` / `隔`），不是一份排队好的候选。所以纠错只能靠**读这句话的 agent 自己有仓库上下文**
    ——它多半能把 `Destok那个Lin包` 解回 `desktop/link`。这条要接受，不要指望识别本身干净。

| 手段 | 结果 |

| `AnalysisContext.contextualStrings`（偏置词表） | **完全无效**。原句「打开 tachibadge 的 kubeconfig，把 rasterizer 那个 pod 重启一下」，词表里就放着 `tachibadge` / `kubeconfig` / `rasterizer` / `pod` 四个词——加与不加，输出**一字不差**（`Twecheack的 Qubecomefic but restriser那个 part`）。 |

**两种失败模式都出现过，正好说明为什么判据要两层**：

- **en-US 遇到中文 → 音译垃圾**：`, , , , ,` 或 `Xian Pao Yi Xian Ling, may want Ti Ziao`。
  置信度很低（0.00 – 0.31），所以单比置信度也能排除它。
- **en-US 遇到中文但只抓到半句 → 残缺却自信**：`看一下 badge 的 RSSI…` 的 8 kHz 那版，
  en-US 给 `Hi, R S S I, her battery level. Hi`，**conf 0.67**，而 zh-CN 是 0.80——
  只差 0.13。**置信度说的是「我说得对不对」，不是「我听全了没有」**。这就是「汉字优先」
  那条硬规则值钱的地方：它在这句上是确定的，不靠 0.13 的裕度。

**复跑的出入（第 5 轮，`./run.sh 5`）**：那一轮的六句话是照本表补全的（本表只写了前半句），
所以不是同一批音频——结果是 **17/18**，而唯一那次出错恰好落在**第二层判据**上：

```
please revert that commit and rerun the tests        ← 纯英文句，16 kHz ADPCM 那版
  zh 0.56 / en 0.55    无汉字，比置信度 → 选 zh ✗
      zh: Plaser that comitenyroun the test.
      en: Please revert that commit, then rerun the tests.
```

两个 conf **差 0.01**，而 zh-CN 那串是音译垃圾。所以准确的说法是：**「汉字优先」那层是稳的
（中文句全中），脆的是第二层**——纯英文句上「比置信度」会被音译结果险胜。设备上大概率的
输入是中文，这个代价可以接受，但别把第二层当成可靠判据。

### 表 7：8 kHz 的代价（§4 把 8 kHz 降为退路的依据）

同一句短句（`把这个 commit revert 掉，然后 rerun 一下测试，最后 push 到 main`）：

| 音频 | zh-CN 的转写 |
| --- | --- |
| 16 kHz 无损 | 把这个 **commit** **revert**掉，然后 **reround**一下测试最后 **pushop** **mean**。 |
| 16 kHz ADPCM | 把这个 **commit** **rivert**掉，然后 **rerom**一下测试最后 **pushop** **main**。 |
| 8 kHz ADPCM | 把这个 **commit** **reverte**掉，然后 **relam**一下测试最后**通时到内**。 |

最后一行里 `push 到 main` 整个变成汉字 `通时到内`——**英文词连形态都没了**，这不是同一量级的
抖动。长句上量不出来（表 3 的四种变体确实同量级），短句上会冒出来。样本少，不下「8 kHz 一定
更差」的结论，只下「**8 kHz 的代价不是零**」，所以它退成带宽不够时的退路。

### 表 8：流式入口（不落盘那条路，§7）

§8 承诺了音频不落盘，所以正式实现不能走 `analyzeSequence(from: AVAudioFile)`。验的是另一条：
把裸 Int16 样本包成 `AVAudioPCMBuffer` → 喂 `AsyncStream<AnalyzerInput>` →
`analyzer.start(inputSequence:)` → `finalizeAndFinishThroughEndOfInput()`。

| 项 | 结果 |
| --- | --- |
| 结果 | 与文件模式**逐字一致**（`Destok`/`领`/`pla`/`Rit`/`Gotes` 一字不差） |
| 块大小 512 vs 1600 样本 | **无差别**（逐字相同） |
| 首次（冷启动） | 901 ms |
| 之后（11.2 s 音频） | 272 ms |

所以垫片的入参就是「`[]int16` + 采样率」，全程不写磁盘。**第 6 轮（`./run.sh 6`）复跑**：
6/6 与文件模式逐字一致、每块 512 与 1600 样本无差别，冷启动 ~0.86s、之后 ~0.21s
（本表的 901ms / 272ms 是另一次，同一量级）。

### 资产的分布（决定默认语言）

探针机器上 `SpeechTranscriber.installedLocales` 有十一种：
`en_IE, en_ZA, en_SG, en_US, en_AU, en_NZ, zh_TW, en_GB, en_IN, en_CA, zh_CN`。
**`zh_TW` / `zh_CN` 是预装的**，`en_US` 是跑这批探针时下载了一次（一次性的，装上就常驻）。
所以**只认中文的机器零下载、完全离线**；启用 §10 那个英文判据会多一次联网下载。

### 补记：真机声学那一关过了

上面所有表的音频都是 `say` 合成再走管线的，验的是**管线**（格式、压缩、语言、延迟），
不是**声学**——「隔着一张桌子的 MEMS 麦克风 + 房间噪声」能不能同样转对，谁也说不准。
**这一条后来在真机上验了**：对着设备说了 7 个字，主机转出来一字不差（16 kHz ADPCM、
8 KB/s、56 片一片不丢、转写 1.1 秒）。协议那头（分片上传、半截会话的超时丢弃、与提示音
共用 codec）也都实现了。

**仍然没验的**：安静环境之外的条件——远一点、有背景音、一句话很长、以及文本里的英文词
被糊掉之后读这句话的 agent 能不能自己解回来（见 §10「已经定了的」里那条）。
