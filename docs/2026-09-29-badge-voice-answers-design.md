# 设备上的语音回答：把「三键打不了字」这件事绕过去

> 状态: 方案（未开工）。**主机侧的可行性已经实测**（四轮探针，数据见附录 B）——§4 的格式、
> §7 的接法、§10 的语言选择都是**量出来的**，不是推的。还剩三件待定，见文末。
> 关联: [2026-09-28-agent-badge-link-design.md](2026-09-28-agent-badge-link-design.md)（链路与协议的基础）、
>       `desktop/link/link.go`、`desktop/asks.go`、`desktop/badge.go`、`llm/provider.go`
> 设备侧仓库: `FoloToy/ai-passport`（`main/badge_voice.c` 等，见 §6）

## 1. 要做什么

**让设备能给出自由文本的答案**——用说的。

基础那份设计里有一条明确不做：「不做设备端自由文本输入。三键打不了字，模型提的『无选项填空题』
在设备上显示『需要在电脑上回答』」。这条限制的真实代价是：**人不在电脑前时，那类问题只能干等**，
而这块设备存在的全部意义正是「人不在电脑前」。

**绕过去的办法是分工，不是妥协**：设备只当话筒（采集 + 压缩 + 发上去），**转写在主机**（那本来
就有模型）。设备依然打不了字——限制没被违反，它只是不再是终点。

用途两处，v1 只做第一处：

1. **无选项的填空题**（v1）：按下说话，转写文本**就是答案**。
2. **给一个决定补一句理由**（待定，见 §9）：拒绝一条命令时说「先别删 build/」，走协议里那个
   **已经留着、两端都没用**的 `annotations` 字段。模型知道「为什么」比只知道「拒绝」有用得多。

**明确不做**：设备端转写（它的算力与功耗都不该花在这上面）；常开麦克风（§8）；把音频当聊天
的多模态输入喂模型（那要模型支持音频 part，而我们要的是**文本**答案，不是第二套语义）；也**不走
llm provider**——本机就能转，还不用联网（见 §7）。

## 2. 为什么是「设备只当话筒」

与整条链路同一条架构原则：**语义留在主机**。设备不知道 `allow_once` 是什么意思、不知道自己在不在
前台、不知道用户在看哪个会话——同理，它也不该知道「这句话是什么意思」。它只负责把一段声音变成
一串字节送上去。

顺带三个好处：转写模型/服务换了设备端一行不用改；设备端要测的仍然是纯逻辑（采样没到下限、
超了上限、链路断了怎么办）；音频**不进**设备的历史，不占它的 flash。

## 3. 交互

**按住确定说话**（在「无选项填空题」那一屏上）：

```
    ┌──────────────────────────┐
    │ (1/1) 一个问题            │   ← 标题栏照旧
    │ ┌──────────────────────┐ │
    │ │ 这道题没有选项，可以  │ │   ← 题面（照旧，可翻屏）
    │ │ 按住确定说话。        │ │
    │ └──────────────────────┘ │
    │ ● 录音中 3.2s / 6s       │   ← 录音时：红点 + 已录时长 + 上限倒计时
    │ 松手发送 · 确定取消?     │   ← 提示跟着手势走（和翻屏那套一致）
    └──────────────────────────┘
```

- **进入**：那一屏上长按确定（现在的键位图上，这一屏的「提交」本来没有含义——没有选项可提交），
  于是这个手势是**空着的**，不需要抢别的键。
- **开始/结束**：按下即开始采集；**松手即结束并发送**。
  - BSP 的按键事件是 `PRESS / CLICK / DOUBLE / LONG`——**没有 release**。所以「松手」靠轮询
    `bsp_button_read_mv()` 判：录音任务每 50ms 读一次那个 ADC 节点，回到松开档位就是松手。
    （函数本来就有，是留给分压标定的；只读，不碰按钮组件自己的采样。）
  - 备选（若轮询在真机上不稳）：改成 toggle——长按开始、再长按结束，上限自动停。手感差一截，
    但完全不依赖 ADC 时序。
- **上下限**：短于 **0.3s** 视为误触（屏幕提示「太短了」）；到 **上限**（见 §4 的时长账）自动结束
  并发送——不让人录到链路塞满才发现。
- **发送中**：那一屏换成「发送中… 3.1s / 5.0s」（按已发送字节数），成功＝主机把这条 ask 答掉了
  （设备侧收到 `ask_gone` 自己就撤屏，不需要新消息）；失败＝复用现成的 `error` 回音（§5）。
- **取消**：录音中短按确定＝丢弃（手滑了不用发上去）。这需要屏幕说清楚，否则「按一下没了」很像坏了。

## 4. 传输与格式：先把带宽量出来

这段是这件事的**工程核心**，而且**第一件事是量**——不是估。

**Step 0（动手第一件事）**：让设备吐 64 KB 假数据（一条 `@@` 行，走 notify），主机侧计时。
设计文档里已经有一条反面教材：BLE 上一次写超 182 字节会被静默丢掉，而那个上限是**实测**出来的。
同样的道理，这条链路的**可持续吞吐**必须实测，否则所有的「几秒能传完」都是猜。

**格式**：**8 kHz / 单声道 / IMA ADPCM（4 bit）= 4 KB/s**。这是**实测**选的，不是算出来的
（数据见附录 B）：

| 方案 | 码率 | 6 秒的字节数 | 实测结论 |
| --- | --- | --- | --- |
| 16 kHz / 16 bit | 32 KB/s | 192 KB | 不现实（若实测 4 KB/s，要传 48 秒） |
| 16 kHz / IMA ADPCM (4 bit) | 8 KB/s | 48 KB | 可用 |
| **8 kHz / IMA ADPCM (4 bit)** | **4 KB/s** | **24 KB** | **选它**：识别质量与 16 kHz 无损**没有可辨差别** |
| 8 kHz / 16 bit | 16 KB/s | 96 KB | 比上面多占 4 倍带宽，换不到东西 |

两条实测结论决定了这个选择：

1. **8 kHz 不掉分**。同一个句子，8 kHz 与 16 kHz 的转写结果只在个别字上不同，错误率同一量级——
   因为 `SpeechTranscriber` 的**原生输入就是 8 kHz 或 16 kHz 单声道 Int16**（附录 B 表 1），
   16 kHz 并没有换来更好的声学建模。既然如此就用 8 kHz。
2. **ADPCM 4:1 不掉分**。手工实现的 IMA ADPCM 编码→解码往返之后，转写结果与无损输入同级
   （有的句子甚至更像对的）。所以「省带宽」这件事在识别率上**不要付代价**——尽管付。

剩下的唯一约束是**链路可持续吞吐**（P0 要量的那个数）：24 KB 在 4 KB/s 的链路上传 6 秒，
在 2 KB/s 上就要 12 秒。若实测吞吐低于 2 KB/s，先把时长上限砍到 3 秒再谈别的。

**时长上限 = 字节上限 ÷ 实测码率**，写成一个命名常量，和 BSP 的 `BADGE_*` 一样放在一处。

**分片**：`base64` 编码（4/3 膨胀），每片 512 字节原始数据 → 一条 ~700 字节的 JSON 行。
设备侧的发送路径本来就按 MTU 切片（`badge_ble_send`），所以一条 700 字节的行 = 3 个 notify，没问题。

## 5. 协议（设备 → 主机）

沿用行分隔 JSON + `@@` 前缀，三条新消息：

```json
{"t":"voice_begin","seq":51,"ref":43,"codec":"ima-adpcm","hz":8000,"bytes":24576}
{"t":"voice_chunk","seq":52,"ref":43,"data":"<512 字节的 base64>"}     // × N
{"t":"voice_end","seq":53,"ref":43,"parts":96}
```

- **为什么不是一条大行**：一条 64 KB 的行要求双方一起把它捧在内存里，中途失败就整条重来；分片
  之后丢一片只损失一片，而且**进度可见**（设备能显示「已发 3.1/5.0 秒」，这在一条大行上是做不到的）。
- **`ref`**：语音属于哪一条等待（主机用它把答案填回正确的那条；一条过期的语音必须被拒——和
  `answer` 的 ref 校验同一条规矩）。
- **`bytes` / `parts`**：让主机能提前发现「收不满」（链路断了），而不是把半截音频送去转写。
- **失败回音**：复用现成的 `error` 消息（`{"t":"error","ref":43,"message":"…"}`）：转写服务没配、
  音频太短、解码失败、超时——都用它说，用户屏幕上就能看见，而不是「按了半天没反应」。
- **不需要新的主机→设备消息**：转写成功后主机把这条 ask 答掉，设备收到 `ask_gone` 自己撤屏。

**这条链路上的信任边界没变**：BLE 那条已经要求「已认证加密」才说话（MITM 配对 + 6 位码）；
语音是**内容**，和屏幕上那些字同级。TCP/WiFi 将来照旧需要应用层密钥（基础那份文档 §9.1）。

## 6. 设备侧实现

- **`main/badge_voice.c/.h`：自己的任务，独占麦克风**。理由和提示音一样：`bsp_audio_read` 会阻塞，
  而按 BSP 的硬规矩，PCM 读写必须待在 worker task 里、且休眠前要停掉 I/O。
  - 采集：`bsp_audio_set_format(8000, 16, 1)` → 按块 `bsp_audio_read` → IMA 编码 → 入队。
  - 发送：编码后的片交给 `send_line`（那条既有的出方向路由，BLE/串口不用它操心）。
  - 结束：停采集 → （音频不睡，因为提示音那条也用它；两处共用一把「谁在用 codec」的约定，
    见 §8 的边界）。
- **状态机多一态**：`BADGE_VOICE_IDLE / RECORDING / SENDING`，放进 `badge_state`（纯逻辑、主机可测）：
  「什么时候能开始录」「录多久必须停」「松手后还能不能取消」都是纯判定，不需要硬件。
- **界面**：录音/发送各一屏（或复用待答屏换掉选项区），提示音那条规矩照旧——**录音中不熄屏**
  （屏幕上正显示时长与上限，熄了等于把手上的操作藏起来）。
- **协议编码**：`badge_proto.c` 加三条编码（纯逻辑、主机可测，和 `answer` 的编码同一套写法）。

## 7. 主机侧实现

- **`desktop/link`**：`Server.handle` 认这三条消息 → 按 `ref` 攒进一个缓冲区（有上限、有超时的
  半截会话表：链路断在中间不会永久留着一块内存）→ `voice_end` 时交出 `[]byte`。
- **解码**：IMA ADPCM → 8 kHz PCM（~30 行，放 `pkg/audio`？见待定 3）。
- **转写走 macOS 自己的 `Speech.framework`**，不走 llm provider（两者都不需要：本机就能做，而且
  **不联网**）。用的是 macOS 26 的新 API（`SpeechAnalyzer` + `SpeechTranscriber`），**不是**老的
  `SFSpeechRecognizer`——理由见下面第一条，这是实测查明的：
  - **⚠ 这套新 API 只有 Swift 有**。`SpeechAnalyzer` / `SpeechTranscriber` / `AssetInventory`
    在 ObjC 头文件里**不存在**，只有老的 `SFSpeechRecognizer`。所以**不能**照抄
    `desktop/webview_awake_darwin.go` 那个「内联 ObjC」的模式——那条路走不通。
    **垫片必须用 Swift**：`desktop/stt/speech_darwin.swift`（或 .m + swift 混编），由一个
    `go:generate`/构建脚本用 `swiftc` 编成产物再链进来；`speech_other.go` 给非 darwin 一份
    「这台机器没有这个能力」的桩。**这是这个方案引入的唯一一处新构建环节**，动手第一件事是把它
    跑通（一个能编译、能被 cgo 调到的空 Swift 函数就够）。
  - **原地（on-device）识别，没有配额**。新 API 全是本机模型，音频不出机器；老 API 那个
    「每天 1000 次」的上传配额与我们无关。
  - **喂 PCM 用 `analyzer.analyzeSequence(from: AVAudioFile)` 或 `AnalyzerInput` 缓冲区，不写
    临时文件**：§8 承诺了「音频不落盘」，为了转写破掉自己的承诺不值得。（`AVAudioFile` 那条
    要求先落盘，所以正式实现走 `AnalyzerInput(buffer:)` 的流式入口。）
  - **语言与资产**：`SpeechTranscriber(locale:preset:.transcription)`。资产用
    `AssetInventory.status(forModules:)` 查；`installed` 才离线可用，否则要
    `assetInstallationRequest` + `downloadAndInstall()`（**这一步联网**，是一次性的）。
    本机实测：`zh_CN` / `zh_TW` **预装**，`en_US` 需要下载——所以**默认 zh-CN 的机器上零下载**。
    没资产**不能装死**：回一条 `{"t":"error",…}`，屏幕上看得到。
  - **异步 + 超时**：识别是 `async` 的。Go 这侧用一个带超时（~30 秒）的等待把结果收回来；卡住
    不能把回答这条路径一起挂住。
  - **一个新的 TCC 权限**：`NSSpeechRecognitionUsageDescription`（`Info.plist` 与 `Info.dev.plist`
    都要加，和蓝牙那个键同一个位置）。⚠ 和蓝牙那次一模一样的坑：授权归因给**responsible process**，
    而且判定发生在**第一次调用**时——所以老 app 包里的二进制会静默失败，测试从 app 里跑也会继承它。
    （探针正是因此在 `.app` 里跑，而不是裸 CLI：裸 CLI 的 responsible process 是终端，终端没有
    这个键，结果是直接崩。）
- **填回**：转写文本作为那条 ask 的答案（`AnswerQuestion`），走的是和前端回答**同一个入口**——
  所以「一条过期的等待必须被拒」那套校验自动生效。
- **不动的东西**：协议其余部分、状态机、设备 UI 的其余屏、提示音。

## 8. 边界与失败

- **麦克风只在按下与松手之间开着**。没有常开、没有「环境音」模式——这条要写进代码注释，也要
  写进 README：一块放在桌上的设备，麦克风的行为必须是可以一眼说清的。
- **音频不落盘**。整段留在内存里，转写完即丢（要不要留档见待定 3）。
- **链路断在录音中间**：`voice_begin` 已经发出去了，主机那边攒了半截——靠超时丢掉（§7）。
  设备这边显示「发送失败」，用户重录。**不做断点续传**：一条 6 秒的留言不值得。
- **与提示音共用 codec**：两边都碰 ES8311（提示音要放、录音要收），而 BSP 的约定是「调用方串行化
  格式/休眠/唤醒，且切换前停止所有 PCM 读写」。所以要有一把锁（或一个「codec 现在归谁」的约定），
  否则「正在录音时来了一声提示音」就是一次格式互踩。**这是这件事里最容易出错的地方。**
- **低电时**：录音 + 传输是最费电的一幕（麦克风 + 射频同时开）。要不要在电量低于 N% 时拒绝录音，
  见待定。
- **一秒能录多长**：上限自动停；短于 0.3s 丢弃；连按不叠加（有状态机兜着）。

## 9. 分阶段

| 阶段 | 内容 | 出口标准 |
| --- | --- | --- |
| **P0** | 两件小事，都是「先证明路是通的」：① 量带宽——设备吐 64 KB 假数据、主机计时；② 把 Swift 垫片编译链路跑通（§7 那条警告） | ① 得到**可持续吞吐**（KB/s），它决定时长上限；② 一个空 Swift 函数能被 cgo 调到并返回 |
| **P1** | 打通「按下 → 录 → 分片上传 → 主机解码 → 转写 → 当答案填回」 | 真机上：对着设备说一句话，desktop 的问题卡收到那句文本 |
| **P2** | 体验：录音屏、倒计时、取消、太短/失败的提示、低电策略 | 不看文档也知道怎么用 |
| **待定** | 权限决定的 `annotations` 补充说明（§1 用途 2） | 另开一轮，协议已经留了字段 |

## 10. 待定（动手前要定的三件事）

1. **时长上限**：先按 6 秒（24 KB）设计，P0 量完带宽再定；可以接受更短（3 秒）吗？
2. **音频要不要留档**：默认不留（内存里转写完即丢）。要留就落在 `~/.tachi/` 下某个目录，
   并且默认关——一块桌上的设备悄悄留下人声是另一类东西。
3. **`pkg/audio` 还是别的家**：ADPCM 编解码是业务无关的纯逻辑，按仓库规矩该进 `pkg/`（设备侧
   那份 C 编解码是另一份实现，两边都要有各自的测试——这正是「协议两端各写一遍」的代价）。

### 已经定了的

- **识别用哪个语言**：**单一 locale，默认 `zh-CN`**（配置项 `voice.locale` 可改）。
  实测数据（附录 B 表 2）说明为什么不做双模块、不做自动判语言：
  - **双模块不融合**。一个 analyzer 里同时挂 zh + en 两个 transcriber，两边**各自独立**转写整段
    音频，结果和单独跑一模一样——不是「按语种分段拼接」。想要那种效果得自己做时轴对齐，而
    `SpeechDetector` **只报「有语音/无语音」，不判语种**，两个前提都不成立。
  - **中英混说：zh-CN 一个模块就够用**。中文句子里嵌的英文词大多能出来（`commit` / `revert` /
    `RSSI` 都活着），会糊的是不常见的那些：`desktop`→`Destok`、`link`→`Lin`、`ble`→`fla`、
    `read`→`Rid`、`main`→`man`、`go test`→`gotest`。en-US 模块识别中文是垃圾。
  - **两条纠错路都堵死**：`AnalysisContext.contextualStrings`（偏置词表）**完全无效**——把目标词
    原样放进词表，输出一字不差；`preset: .transcriptionWithAlternatives` 的备选**只是尾部碎片**
    （`隔。` / `隔`），不是一份排队好的候选。所以纠错只能靠**读这句话的 agent 自己有仓库上下文**
    ——它多半能把 `Destok那个Lin包` 解回 `desktop/link`。这条要接受，不要指望识别本身干净。

## 附录 B：主机侧转写的实测数据

四轮探针，全部在 macOS 26.3.1 / Apple Silicon 上跑。**结论不是推的，是量出来的**——而且
**不用人开口**：句子用 `say` 合成（Tingting / Samantha 两个音色），再过 `afconvert` 转成
16 kHz / 单声道 / Int16（和链路里要传的格式一样）。探针**必须打包成 `.app` 跑**，理由见 §7 的
TCC 那条。

### 表 1：原生输入格式（决定设备该采什么）

| 模块 | 可接受格式 |
| --- | --- |
| `SpeechTranscriber(zh-CN)` | 16000 Hz / 1ch / Int16，8000 Hz / 1ch / Int16 |
| `SpeechTranscriber(en-US)` | 同上（仅顺序不同） |

**只有这两个采样率，没有别的**——设备端采 8 kHz 或 16 kHz 都是「喂给它的原生格式」，不需要重采样。

### 表 2：中英混说的识别质量（原句 → 转写）

| 原句 | zh-CN 单一模块 | en-US 单一模块 |
| --- | --- | --- |
| 把这个 commit revert 掉，然后 rerun 一下测试，最后 push 到 main | 把这个 **commit** **revert**掉，然后 **reround**一下测试最后 **pushop** **mean**。 | Magic, commit, river, Yang Ho, Ri, Rong, Yian, sushi, to, ho, to, shia, main. |
| 看一下 badge 的 RSSI 和 battery level，还有 BLE 连接间隔 | 看一下 **Bec**的 **RSSI**和 **Bentrylevel**还有什么连接间隔。 | Hi Yisian, Ben, the R S S I, her battery level. Hi, you, family. |
| 帮我看一下 desktop 那个 link 包里面的 ble 实现，我怀疑 read 返回之后没有检查连接状态，你把 go test 跑一下确认没有回归 | 帮我看一下 **Destok**那个 **Lin**包里面的 **fla**实现，我怀疑 **Rid**返回之后没有检查连接状态，你把 **gotest**好一下确认没有回归。 | （空） |
| 打开 tachibadge 的 kubeconfig，把 rasterizer 那个 pod 重启一下 | 打开 **Twecheack**的 **Qubecomefic** but **restriser**那个 **part**重启一下。 | — |

**读法**：纯中文几乎逐字正确；嵌进中文的英文词，**常见的活着、不常见的糊**。糊掉的那些恰好是
文件/包名（`desktop` / `link` / `ble` / `read` / `main` / `go test`）——也就是最该准的部分。
**这不能靠识别本身解决**（下面表 4 试过了），只能靠读这句话的 agent 有仓库上下文。

### 表 3：有损压缩与采样率（决定 §4 的格式）

同一句长句（11.2 秒），四种音频走同一个模块：

| 变体 | 码率 | 转写结果 |
| --- | --- | --- |
| 16 kHz 无损 | 32 KB/s | 帮我看一下 **Destok**那个 **Lin**包里面的 **fla**实现，我怀疑 **Rid**返回之后… |
| 16 kHz ADPCM 4:1 | 8 KB/s | 帮我看一下 **Destok**那个 **领**包里面的 **plas**实现，我怀疑 **Rid**返回之后… |
| 8 kHz 无损 | 16 KB/s | 帮我看一下 **Destok**那个 **Lin**包里面的 **plas**实现，… **Gotest**好一下… |
| 8 kHz ADPCM 4:1 | 4 KB/s | …**Destok**那个 **面包**里面的 **pla**实现…**Rit**返回… |

**四种变体的错误率同一量级**——`ble` 在四行里分别是 `fla` / `plas` / `plas` / `pla`，全是错的，
但错得一样。所以：**降到 8 kHz、再压 4:1，在识别率上没付代价**。短句（6.2 秒）上同理：
`Bentrylevel` → `Benterylevel` → `Benterylevel` → `Beterylevel`。选最省的那个（8 kHz ADPCM）。

### 表 4：两条纠错路，都不通

| 手段 | 结果 |
| --- | --- |
| `AnalysisContext.contextualStrings`（偏置词表） | **完全无效**。原句「打开 tachibadge 的 kubeconfig，把 rasterizer 那个 pod 重启一下」，词表里就放着 `tachibadge` / `kubeconfig` / `rasterizer` / `pod` 四个词——加与不加，输出**一字不差**（`Twecheack的 Qubecomefic but restriser那个 part`）。 |
| `preset: .transcriptionWithAlternatives` | **无用**。最后一条结果里的 `alternatives` 只有 `["隔。", "隔"]`——是尾部碎片，不是排队好的候选句。 |
| 一个 analyzer 挂 zh + en 两个模块 | **不融合**。两个模块各自独立转写整段音频，结果与各跑各的几乎一致（差别只在标点）。 |
| `SpeechDetector` 判语种 | **做不到**。它的 `Result` 只有 `speechDetected: Bool`——是 VAD，不是语言识别。 |

**表 4 的意义**：所有「识别完再自动纠错」的聪明办法都被否掉了。设计上接受「转写有噪声」，
把纠错的指望放在**读这句话的 agent 身上**（它有仓库上下文，`Destok那个Lin包` 对它不是难题）。

### 表 5：延迟（决定体验）

| 音频时长 | 转写耗时 | 倍速 |
| --- | --- | --- |
| 6.2 s | ~150 ms | ~40× 实时 |
| 11.2 s | ~210 ms | ~53× 实时 |
| 14.5 s | ~255 ms | ~57× 实时 |

**远快于实时**（首次调用含冷启动，约 800 ms）。所以链路那头的瓶颈是**传输，不是转写**——
语音上传完到出文本几乎是瞬时的，用户的等待全在 §4 那个「已发 3.1/5.0 秒」上。

### 资产的分布（决定默认语言）

探针机器上 `SpeechTranscriber.installedLocales` = **`zh_TW, zh_CN`**（预装），
`en_US` 状态是 `supported`（即需要下载）。所以**默认 zh-CN 的机器上，识别零下载、完全离线**。

### 这轮没验的

- **真机麦克风的声学**。`say` 合成的声音比「隔着一张桌子的 MEMS 麦克风 + 房间噪声」干净得多。
  上面的表证明的是**管线**（格式、压缩、语言、延迟），不是**声学**。最后一步得在真机上对着
  设备说一句——那需要 §6 的设备端先写出来。**这是这套方案剩下最大的不确定性。**
