Hashline 编辑算法

从协议设计到两阶段事务的完整解析 — 附 Tachi(Go) 与 oh-my-pi(TypeScript) 实现对比

本文档基于 oh-my-pi (TypeScript / Bun) 和 Tachi (Go) 两个独立实现对比撰写。
两者都以 oh-my-pi 的 hashline 协议为参考，但在细节上有显著差异。

一、设计动机：为什么需要 Hashline？

传统字符串替换编辑（old_string → new_string）有三个致命弱点：

  1. 歧义匹配 — 如果 "}" 在文件中出现 10 次，LLM 需要提供足够大的上下文才能唯一定位
  2. 编码陷阱 — 不可见字符（全角空格、零宽连接符、curly quote）导致匹配失败
  3. 无版本绑定 — 读文件后如果被 lint-staged / git checkout 等外部进程修改了，编辑会作用于错误内容上

Hashline 用行号锚定 + 内容哈希版本绑定解决了这三个问题：LLM 按行号精确瞄准目标，快照 tag 确保文件未被篡改。

核心思想可以总结为三点：

  • 🔢 行号即精确锚点 — 用数字代替模糊的字符串匹配
  • 🔐 快照 tag 即乐观锁 — 基于整个文件内容的哈希，保证读写的原子性
  • 🔄 两阶段事务 — Prepare（验证所有）→ Commit（全部落盘），支持多文件回滚

二、Section 协议格式

2.1 基本结构

# 文件头：¶路径#4位16进制tag ¶src/main.go#A1F0

# 可选：上下文校验行（N:预期内容） 1:package main
2:
3:import "fmt"

# 操作命令 + body replace 5..5:
+func greet(name string) string {
+ return fmt.Sprintf("Hello, %s", name)
+}

delete 8..10

insert after 3:
+import "os"

insert head:
+// Code generated; DO NOT EDIT.

insert tail:
+
+// End of file

一个 Section 对应一个文件。多个 Section 可以出现在同一个 EditFile 调用中（用 ¶ header 分隔）。

2.2 操作类型全景

操作语法Body含义
replace replace N..M: 需要 +行 删除第 N-M 行，用 body 行替换
delete delete N..M 不允许 删除第 N-M 行（无冒号）
insert before insert before N: 需要 +行 在第 N 行之前插入
insert after insert after N: 需要 +行 在第 N 行之后插入
insert head insert head: 需要 +行 在文件开头插入
insert tail insert tail: 需要 +行 在文件末尾插入
关键规则：
• 行号始终引用原始文件（ReadFile 时看到的编号），操作顺序不影响行号
• replace N..N: 就是替换一行；body 可以有任意多行
• delete N 等价于 delete N..N
• 想插入一个空行？写 +（+ 后无内容）
• 想插入字面 -text？写 +-text

三、快照存储与 Tag 验证

3.1 双层哈希设计

Tag 看起来像 A1F0（4 个 hex 字符），但背后是完整的 SHA-256。

oh-my-pi (TS) TypeScript

// format.ts — computeFileHash
function normalizeFileHashText(text: string): string {
  return text.replace(/[ \t\r]+(?=\n|$)/g, "");
}

export function computeFileHash(text: string): string {
  const normalized = normalizeFileHashText(text);
  const low16 = Bun.hash.xxHash32(normalized, 0) & 0xffff;
  return low16.toString(16).padStart(4, "0").toUpperCase();
}

• 用 xxHash32（极快）取低 16 bit → 4 hex
• 哈希前做 per-line trailing whitespace strip
• 这样可以容忍编辑器和 CI 的尾空白差异

Tachi (Go) Go

// hash.go — ComputeTag
func ComputeTag(content string) string {
  return computeTagBytes(content, 2)
}

func computeTagBytes(content string, numBytes int) string {
  h := sha256.Sum256([]byte(content))
  return hex.EncodeToString(h[:numBytes])
}

• 用 SHA-256 取前 2 字节 → 4 hex
• 不做 trailing whitespace strip
• 因此对编辑器自动 trim 行为更敏感

3.2 SnapshotStore：内容寻址的版本管理

SnapshotStore 内部结构
// 双层索引：path → tag → SnapshotEntry
snapshots: {
  "src/main.go": {
    "a1f0": { tag: "a1f0", fullHash: "e3b0c442...", timestamp: ... },
    "b2c1": { tag: "b2c1", fullHash: "6a09e667...", timestamp: ... },
  },
  "src/utils.go": {
    "f0a3": { tag: "f0a3", fullHash: "...", timestamp: ... },
  }
}

Record(path, content) — ReadFile 调用：存快照，返回 4-hex tag
Verify(path, tag, currentContent) — Prepare 调用：用 FullHash 精确比对，防止 hash 碰撞
InvalidateTag(path, tag) — 回滚时使用：删掉过期 tag

oh-my-pi 的优势：
• SnapshotStore.byHash(path, hash) — 按 tag 反查完整文件文本
• 这是 Recovery 机制的前提：当 live 文件与 tag 不匹配时，可以用存储的历史版本做 3-way merge
• Tachi 的 SnapshotStore 没有这个反查能力，所以 Recovery 无法实现

关键点：所有 Section 的 Prepare 全部通过后，才开始 Commit。任何一个失败，整个调用返回错误，不会有部分写入。

4.2 Commit 阶段

Commit 是单个 Section 的写入，步骤简单：

  1. Write 新内容到磁盘（保留原 BOM 和行尾风格 — oh-my-pi 独有）
  2. Record 新快照（返回新的 tag 给 LLM 锚定下一轮编辑）
  3. 如果某个 Commit 失败（磁盘满等），回滚已写入的文件 + invalidate 其 tag

4.3 Apply 的核心算法

oh-my-pi TypeScript

// apply.ts — 原子化编辑模型
// parse 阶段：每个 replace N..M: + body
//   展开为：
//     N 个 "insert" (replacement body 行)
//   + (M-N+1) 个 "delete" (原行)

// applyEdits 阶段：
// 1. bucket anchor edits by line
// 2. process bottom-up (high line → low)
//    这样行号偏移不影响未处理的 bucket
// 3. per line: beforeInsert + replacement + afterInsert
// 4. repairReplacementBoundaries
//    → boundary echo detection
//    → delimiter balance repair

Tachi Go

// patcher.go — 单 pass 合并
// applyOperations 用 map[int]*lineOp
// 收集每个原始行号的操作：

type lineOp struct {
  deleted      bool
  replacement  []string
  insertBefore []string
  insertAfter  []string
}

// 一次遍历原始行：
// for each line:
//   → insertBefore
//   → if deleted: replacement (skip original)
//   → else: original line
//   → insertAfter

oh-my-pi 的设计更"原子化"（把 replace 拆成 insert+delete 原子操作，bucket 化后 bottom-up），而 Tachi 用了更直接的"行号→操作"映射。两者的正确性在多个操作作用于同一行号时表现不同，这也是我们后续发现 bug 的根源。

五、Recovery（oh-my-pi 独有）

当 Verify(tag, currentContent) 失败时（文件在 ReadFile 后被外部进程修改），oh-my-pi 不直接报错，而是尝试三种恢复策略：

Recovery 决策树
Tag 不匹配 → 查找历史版本

  ┌─ 找到历史版本？
  │
  ├─ YES ── 是 HEAD（外部修改）？
  │         ├─ 在历史版本上 apply → 3-way-merge 到 live
  │         │   成功？→ ✅ 应用 + RECOVERY_EXTERNAL_WARNING
  │         │   失败 ↓
  │         │
  │         └─ 是 session-chain（自己在 session 内改过）？
  │            ├─ 行数相等 AND anchor 行内容未变？
  │            │  → replay 在 live content 上
  │            │    成功？→ ✅ RECOVERY_SESSION_REPLAY_WARNING
  │            │    失败？→ ❌ mismatcherror
  │            │
  │            └─ line count diff → ❌ mismatcherror
  │
  └─ NO 历史版本 → ❌ mismatchError
还有一个捷径：如果所有操作都是 insert head / insert tail（位置稳定，不受内容变化影响），即使 tag 不匹配，oh-my-pi 也只会发一个 warning 而不是 hard error。Tachi 的 Fix #4 正是移植了这个逻辑。

六、两个实现的关键差异（及发现的 Bug）

P0 Bug #1：CRLF 文件 Tag 必然不匹配

根因：ReadFile 存快照时用的是原始字节（含 \r\n）， 但 Patcher.OSFileSystem.Read() 已经 normalizeLineEndings（\r\n → \n）， hash 不同 → 首次编辑必失败。

修复：ReadFile 在 Record() 之前也调用 NormalizeLineEndings。

P0 Bug #2：insertAfter 在 deleted 行上被静默丢弃

根因：applyOperations 中 continue 跳过了 insertAfter 代码块。 当 LLM 写 replace 2..2: +新内容 同时 insert after 2: +追加 时，追加内容消失。

修复：在 continue 之前也处理 lo.insertAfter。

P0 Bug #3：空行被当作 Section 分隔符

根因：splitSections 用空行切分 section，但 section 内部 body 也可能有空行（操作之间分隔、+ 插入空行）。

修复：改为按 ¶PATH#TAG header 分隔。

P1 Bug #4：无 head/tail-only stale tag 的降级处理

修复：纯 head/tail 操作对 stale tag 不 fatal，改为 warning + 应用到 live content。

P1 Bug #5：bare body line（无 + 前缀）被静默丢弃

修复：Auto-pipe 进 body 内容（匹配 oh-my-pi 的 BARE_BODY_AUTO_PIPED_WARNING）。

P1 未修复：无完整 Recovery 机制

oh-my-pi 的三阶段 Recovery（3-way-merge / session-chain replay / head-tail warning）Tachi 仅实现了最后一级。 前两级需要 SnapshotStore.byHash() 反查能力和 diff 库支持。

P2 未修复：无 Boundary Echo / Delimiter Balance Repair

oh-my-pi 的 repairReplacementBoundaries 自动修复 LLM 常见的边界错误（range 包含未改动的函数签名/括号）， Tachi 完全没有这类修复。

七、协议设计中的巧妙细节

7.1 上下文校验行（Context Lines）

在操作命令之前，LLM 可以可选地写入 N:预期内容 行作为"二次确认"：

¶config.go#B2C1
15:func (s *Server) Listen(addr string) error {
16: ln, err := net.Listen("tcp", addr)
replace 15..16:
+func (s *Server) Listen(addr string, opts ...Option) error {
+ ln, err := s.createListener(addr, opts...)

Patcher 用 Levenshtein 模糊匹配（默认阈值 0.95）比对上下文行与文件实际内容。这是一个精致的双重保险： tag 保证文件整体未被改过，context line 额外保证「你要改的这几行确实是你以为的那几行」。

7.2 操作顺序独立于行号

所有操作的行号参数始终引用原始文件。无论 section 里有 5 个操作还是 50 个，它们同时基于同一份原始内容计算结果。 这极大降低了 LLM 的认知负担 — 它不需要推算"删掉第 3 行后第 5 行变成了第几行"。

7.3 Content-Addressable 去重

如果两次 ReadFile 读到完全相同的文件内容，Record() 返回同一个 tag。 这不仅节约了存储，更重要的是给了 LLM 一个清晰的信号："你之前看到的文件没变，可以放心继续操作。"

九、总结

Hashline 协议的精髓在于用哈希做乐观锁、用行号做精确索引，把文件编辑变成了一个具备 ACID 特性的小事务。两个实现（oh-my-pi TypeScript 和 Tachi Go）各有侧重：

  • oh-my-pi 是"全功能参考实现"：normalized hash、Recovery、boundary repair、BOM/line-ending 保留、block edit（tree-sitter 感知的语法块替换）
  • Tachi 是"精简版学习者"：核心正确但缺少韧性层（Recovery、boundary repair），在 LLM 不那么"听话"的时候更容易失败

本次发现的 5 个 bug 修复后，Tachi 的编辑成功率会显著提升 — 尤其是 P0 级别的 CRLF mismatch 和 insertAfter 丢弃，这两个是日常使用中最高频的失败场景。
