## P1 落地（2026-09-13）与实现中的四处偏离

落点见 §4，全部按设计实现；以下是实现时新增/调整的部分：

1. **过程条首部多一档文案**：`步数 = 工具调用数`；一轮只有思考、没有工具调用时显示 `思考 N 段`（否则会是毫无意义的 `0 步`）。
2. **diff chip 会顺带展开过程**：`🧾 N files` 的"展开全部 diff"作用于被折叠的工具卡，若不展开过程，点击会看起来毫无反应——所以打开 diff 时一并把该轮的过程展开（收起方向不动它）。
3. **"正在跑的那一步"也在恒显清单里**（设计里只写了失败与阻塞项）：实现时发现它是 P1 里唯一还能回答"在推进吗"的东西——实时条属于 P2——所以未完成的工具卡保持外露，跑完自动归档进过程条。
4. **过程折叠只在对话层**：`TurnPart` 一行未改，`oneoff.tsx` 的旁路面板继续完整回放过程（这正是它存在的意义）。


## P2 落地（2026-09-13）与两处偏离

1. **实时条**：运行中同一行改报"现在在做什么" —— `● 正在 <工具> · <目标> · 第 N 步 · 12.3s`（脉冲点 + 逐秒递增的用时）。措辞收在 `processLiveLine()`（`transcript.ts`），过程条与输入框上方**共用同一句**，避免两处措辞漂移。
2. **~~输入框上方的活动行~~（已移除，当天）**：曾按设计加过 `composer.tsx` 的 `.composer-activity`（同一句活动信息，由调用方格式化，非 live region）。**移除原因**：它只在"有工具在跑"时存在，于是每完成一步就消失、下一条命令又出现 —— 消息区跟着一上一下，视觉噪音大于它的价值；而同一件事对话区里已经有两处（过程条的实时行 + 外露的运行卡），运行中另有停止按钮与侧栏转点。留存即此记录：**要再加这一行，必须先让它恒定占位**（运行期间始终一行，含思考/等待态），否则就是在给布局添抖动。
3. **跟随底部不用改**：现有实现是"每次提交后 `scrollTop = scrollHeight`"，**收缩**同样被覆盖；`transcript-live` 场景实测收起后距底部 0px ✓。
4. **三处实现偏离**：
   - **实时条在"还没东西可折"时也要渲染**：一轮的第一个 part 若是正在跑的调用，它就是外露的（恒显），此时 `folded` 为空 —— 若按"有 fold 才画条"就会在最有用的时刻什么都不显示。所以条件是 `folded.length > 0 || (running && live)`。
   - **无可折叠内容时它不是按钮**：同一情形下没有任何东西可展开，行渲染为 `.static`（无 caret、无 toggle、不可点）——一个点开什么都没有的开关比没有更糟。
   - **运行中的卡不再外露**（P2 之后的修正）：P1 曾把"正在跑的那一次调用"留在折叠之外——那时没有实时条，它是唯一能回答"在推进吗"的东西。有了实时条之后它成了冗余（两者说同一件事），代价却是每完成一步就消失一次、下一条又开始，**下面的正文跟着一上一下**。现在它和别的 part 一样折叠；想看卡本身点开时序即可（卡在里面原地更新）。同理，**被权限卡挂住的那次调用不算"正在跑"**：它的卡已被确认卡替换，实时条不该说「正在执行」。

验证：`tsc` / 前端构建 / 新场景 `transcript-live` 18 断言（实时条文案与脉冲、活动行同句、运行卡外露、回合结束后回摘要且活动行消失、**折叠收缩后仍贴底**）；全套 smoke 18/18。

验证：`tsc` / 前端构建 / 定向 smoke 5 个场景全过（新场景 `transcript-fold` 16 项断言：过程条文案、染红、结论恒显、折叠态只留失败卡、展开后两张都在）；全套 smoke 见提交记录。

## 1. 问题

一轮长执行里，对话区会长成这样：

```
正文 → ▸thinking → 工具卡 → 工具卡 → ▸thinking → 正文 → ▸thinking → 工具卡 …
```

**注意：thinking 与工具卡本身已经是折叠态**（`ThinkingPart` 默认 `collapsed`，`ToolCard` 默认不展开，各自只占一行骨架）。所以噪音不是"内容展开了"，而是**行数**：一轮 30 步就是 30 行骨架，再夹着几段中间说明。

目标（用户原话）：① 仍能看出事情在推进、没卡住；② 需要时可点开看完整时序；③ 信息流更干净。设计另加两条安全阀：**失败不藏**、**阻塞项不折叠**。

## 2. 现状盘点（实施前的事实）

- **parts 的生产**：实时路径 `useTranscript.ts`、历史回放 `lib.ts` 都产出 `Part[]`；渲染统一走 `parts.tsx` 的 `TurnPart`（原子渲染器）——单一渲染路径是既有约定，不要破坏它。
- **`TurnPart` 还被旁路面板复用**：`oneoff.tsx` 用同一套部件回放 `/review`、`/commit` 的过程。**面板的职责就是展示过程**，所以折叠必须发生在**对话层**，不能改 `TurnPart` 的语义。
- **一轮的现有骨架**：user 气泡 → 若干 part → `.msg-footer`（`⏱ 时长 · N iters · ¥成本 · N 积分`）+ 尾部 chips（`完整 diff` / `评审本轮改动`）。
- 已有的同类先例：`NoticePart`（自动压缩）就是"一行事件 + 可展开的体"——本设计沿用它的形状与交互习惯，不新造范式。

## 3. 设计

### 3.1 归纳规则

一轮（一个 assistant turn）内的 part 分两类：

| | 内容 | 默认可见性 |
|---|---|---|
| **过程** | `thinking`、`tool`、以及**非最后一段**的 `text` | 收进过程条，折叠 |
| **结论** | 该轮**最后一段** `text` | **恒显**（正文） |

`notice` 不参与折叠（它本来就是一行事件，独立存在）。

### 3.2 三处界面

1. **过程条（折叠态）** —— 一行，位置在**原位**（用户气泡之后、结论正文之前）：
   `▸ 12 步 · 读了 3 个文件 · 跑了 5 条命令 · 搜了 4 次 · 含 2 段过程说明`
   右侧 `展开时序` 提示可点。整行是一个 `button`（`aria-expanded`）。
2. **实时条（运行中）** —— 同一行的另一种形态，回答"还在动吗"：
   `● 正在 Bash · npm test · 第 7 步 · 12.3s`（脉冲点 + 用时递增）。
   同时在输入框上方保留一条同样的活动信息（眼球在底部时也能看到）。
3. **时序（展开态）** —— **原位**展开，就是今天的渲染原样（thinking 行 + 工具卡 + 中间说明），左侧一条竖线表示"属于同一次过程"。再点收起。

### 3.3 恒显清单（安全阀）

无论折叠状态如何，以下**永不折进过程条**：

- 该轮最后一段结论正文；
- **失败 / 被拒的步骤**：过程条上出现 `⚠ N 步失败`（红），且**那一步的卡片外露**（见 §3.4 的判定）。注意这里只覆盖**已结束**的失败步：运行中的调用不外露（它随每步一现一隐会让正文跳动，见 §3.2）；
- `PermissionForm` / `AskForm`（阻塞项，用户必须能看见）；
- `已停止` / 出错标记；
- `.msg-footer` 与尾部 chips（成本、iters、diff/评审入口）。

### 3.4 过程条的内容（全部由 parts 确定性推导）

| 片段 | 来源 | 说明 |
|---|---|---|
| `N 步` | 过程 part 数 | 常显，是"干了多少"的最短表达 |
| 工具构成 | 按 `Part.name` 归类计数 | `读了 N 个文件 · 跑了 N 条命令 · 改了 N 个文件 · 搜了 N 次`（类别映射按现有工具名，未知归"其它"）|
| `⚠ N 步失败` | `ok === false` 或 `done && !ok` | 有则红字；**不折叠失败步**：展开后仍高亮，且过程条默认展开 |
| `含 N 段过程说明` | 非末尾的 `text` part 数 | 提示"中间还有话"，避免用户以为只有一条正文 |
| 耗时 | **不在过程条上重复** | 交给 `.msg-footer` 的 `⏱`（同一轮只有一个时长口径） |

失败判定用 `Part.ok`（工具是否成功）与 `Part.done`，不看文本内容——不要用 LLM 生成摘要：那会多一次调用，且重启后与历史不一致。

### 3.5 档位（偏好）—— 已决定不做（2026-09-13）

原设计是 `简洁 / 平衡（默认）/ 详细` 三档，存 `desktop_ui.json`（简洁 = 正文 + `N 步`；平衡 = 含工具构成；详细 = 过程直接铺开，等价默认展开），且档位只是默认值、不覆盖单轮手动展开。

**为什么不做**：默认档（平衡）已经把三条目标兑现了（知道在推进 / 可点开看全程 / 界面干净），剩下的差异只是口味；而「想忽然看全程」这件事，**点开那一轮的过程条**已经能随时做到，不需要一个全局开关。等真的出现「频繁想切换」的实证再说——那时更可能的形态是**只加「详细」一档**（一个「默认展开」的开关），而不是三档加一份偏好存储。

保留这段是因为：一个被明确否掉的方向，和没想过的方向不是一回事。

### 3.6 展开状态是展示态

不入库。重开会话一律默认折叠；同一次会话内记住手动展开过的那一轮，**轮末不自动收起**（用户既然点开了，就是在看）。跨会话**不保留**展开态 —— 切走再回来会收起，这是已知取舍（没有档位与持久化之后，规则更简单可预期）。

## 5. smoke 影响面（实测，不是估计）

**按"时间线内的选择器"找，而不是只找 `.tool-status`**：`transcript` 断的是 `.tool-card`，
`oneoff-footer` 断的是 `.tool-name` —— 只 grep 一个会漏掉它们（实测漏了 `transcript`，driver 挂到
1m30s 预算耗尽）。

| 场景 | 原断言 | 迁移后 |
|---|---|---|
| `perm-allow` / `perm-session` | 工具卡存在且 `ok` | 先点开过程条再断言（成功的调用默认收起） |
| `perm-deny` | 工具卡是失败态 | **无需改**：被拒的卡是失败步，本就不折叠 |
| `transcript` | `.tool-card` 有输出且已收尾 | 等结论上屏 → 展开过程条 → 断言卡；另加"结论是最后一块""过程条在结论之前"两条顺序断言 |
| `oneoff-footer` | `.chat .tool-name` 恰好 2 个 | 先展开对话里的过程条再数（同时也让"评审的卡不在对话里"这条更强） |
| `skill-catalog` | 没有工具卡 | 改成"没有工具卡也**没有过程条**"，否则会变成"因为折叠所以看不见"的假通过 |

新增场景：

- **`transcript-fold`**（16 断言）：折叠态只留失败卡 + 结论恒显、点开后两张卡都在、过程条文案含步数与失败数且染红。
- **`transcript-live`**（22 断言）：`sleep 4` 让工具真的在跑 → 实时条文案 + 脉冲点 + 运行卡外露；回合结束后回摘要；**真的展开再收起一次**，断言两次都贴在底部（只读"回合结束后贴底"是空的，那时内容只增长过；这条被补实之后当场揪出了"展开让视图跳走"的回归）。

## 7. 风险与取舍

- **高度收缩**：现有跟随底部盯的是内容盒子的 `ResizeObserver`——**生长**没问题，**收缩**要在 P2 实测（展开/收起发生在流式期间最容易跳）。
- **"agent 是不是没干活"**：折叠会让人误读，靠实时条 + 常显步数抵消；这是本设计的核心赌注。
- **失败多的一轮仍然会长**：有意为之——错误可见 > 整洁。
- **关键结论写在中间**的情况：靠过程条上的 `含 N 段过程说明` 提示召回，点开即见全文（没有「详细档」托底了，所以这条提示本身要在）。
- 不动 `TurnPart` 是有意的：旁路面板（评审/提交）继续完整展示过程，两个界面的差异**只**在"是否折叠"，不在"怎么渲染"。

## 8. 待决问题

1. **过程条要不要显示耗时**？当前取舍：不显示，交给 `.msg-footer` 的 `⏱`（一轮一个时长口径）。若认为"一眼看到 N 步花了 18.4s"更重要，则两处都显示但文案区分（过程条=工具耗时合计，footer=该轮总时长）。
2. **失败轮是否自动展开**？当前取舍：不自动展开，但过程条变红 + 失败卡片外露（避免"自动展开把页面顶掉"）。
3. ~~**简洁档的下限**~~ —— **已关闭**：档位整体不做（§3.5）。
4. **中间说明的取舍**：现在折叠后靠提示召回；是否要把"以句号/换行结尾且较长"的中间说明当作结论一并显示？（倾向不做——规则越简单越可预期。）
